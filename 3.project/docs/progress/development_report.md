# 계약 증빙 자동검수 개선 작업 보고서

이 보고서는 2026년 10월 1일부터 이어서 진행하는 안정화, 로컬 LLM 보완, 성능 평가 준비의 변경 내용과 검증 결과를 기록한다. 팀원이 구현 범위와 다음 작업을 확인하고 최종 설명 문서에 사용할 근거를 찾는 것이 목적이다. 기존에 구현된 기능, 이번 작업에서 바뀐 기능, 아직 실행하지 않은 계획을 구분한다.

## 합의한 범위와 일정

실행 순서는 0번 안정화, 2A 정답표와 기준 성능, 1번 로컬 LLM과 근거 검증, 2B 비교 평가, 3번 업무 흐름 보완, 4번 결과 설명, 선택 5번 검수 에이전트, 6번 제출 문서이다. 필수 범위는 안정화와 평가 준비 및 LLM과 비교 평가이며 10월 5일을 목표로 한다. 10월 7일 저녁에 기능을 동결하고 10월 8일부터 문서와 시연 준비를 진행한다.

3번과 4번은 필수 범위가 끝난 뒤 10월 6일까지 진행하는 권장 범위다. 선택 에이전트는 10월 7일 오전까지 완성하지 못하면 향후 계획으로 돌린다. 안내문의 제출 일정은 설명 문서와 소스 코드 10월 10일, 발표 자료 10월 11일, 발표 10월 12일이다. 기능 동결 후에는 시연과 문서 확인을 우선한다.

평가의 35%는 LLM 사용 여부 하나가 아니라 요구 분석, 구조 설계, AI와 도구의 활용, 결과 신뢰성을 함께 다룬다. LLM을 사용했다는 사실과 실제 성능 개선을 구분해서 보고한다. 할루시네이션을 완전히 해결했다고 표현하지 않고, 근거 검증과 사람 검토로 잘못된 추출의 위험을 줄인 범위를 설명한다.

### 이번 안정화 변경

파일과 이미지 응답을 만든 뒤 감사 기록을 남기도록 변경했다. 마스킹 실패나 존재하지 않는 페이지 요청을 성공한 응답 준비 기록처럼 남기지 않는다. 파일을 전송하는 동안 사용자가 모든 바이트를 받았다는 사실은 확인할 수 없으므로 기존 요청 기록 명칭은 유지한다. 무거운 렌더링과 OCR 전에 읽기 트랜잭션도 종료하여 다른 요청에 영향을 줄이지 않도록 한다.

동시 처리 검증에는 업로드 분석이 대기 중일 때 계약 목록이 응답하는 확인을 추가했다. PDF 미리보기, 가린 PDF 다운로드, 텍스트 미리보기 각각이 대기 중이어도 다른 계약 목록과 원본 다운로드가 완료되는 테스트를 추가했다. 마스킹 실패 및 잘못된 페이지 요청에서 성공 응답에 해당하는 감사 기록이 생기지 않는지도 확인했다.

Git 저장소 루트는 `C:\3조 색인`이다. 그 아래 `tmp`는 기존 `3.project/.gitignore`의 적용 범위 밖이라 실제로 제외되지 않았다. 저장소 루트에 `/tmp/` 제외 규칙을 추가하고 프런트 TypeScript 빌드 캐시도 제외했다. `git check-ignore`로 두 경로가 실제로 제외되는지 확인했다. 이는 Git 제외 설정이며 ZIP에 임의로 폴더 전체를 담는 행위를 막지는 않는다. 제출 ZIP 대상은 별도로 확인한다.

기존 코드의 날짜 처리 등에서 발생한 경고 555개가 남았다. 테스트 실패는 없었으며 경고를 모두 해결했다고 주장하지 않는다. Git 공백 검사도 통과했다. 안정화 단계는 기존에 진행하던 파일 변경과 이번 감사·동시 처리 변경을 검증해 `0927842 fix(pilot): checkpoint stabilized local evidence workflow`로 함께 저장했다. 앱 코드와 기존 화면 등 74개 파일의 체크포인트이며 평가 자료·도구는 별도 작업으로 구분했다. 원격에 push하지 않았다.

## 평가 준비와 사람 확인

최종 평가의 정답표는 아직 확정하지 않았다. 합성 문서, 빈 정답 양식, 라벨링 기준 및 측정 도구를 준비했다. 이후 사용자가 Codex 초안과 Claude 검토를 함께 활용하는 방식에 동의하여 생성 설계 초안과 명시적인 dev 예비 측정을 추가했다. 미확정 초안으로 정식 성능 또는 최종 목표 달성을 주장하지 않는다. 사람 확정이 필요한 정식 측정 명령은 계속 차단된다.

시나리오는 정상 제출, 필수 서류 누락, 공급자 사업자번호 불일치, 합계 불일치, 부가세 별도 계약, 분할 지급, 스캔과 노이즈, 품목 표, 모호한 금액, 공급가액·세액과 합계의 산술 불일치이다. 회사명과 거래는 가상이다. 테스트 사업자번호는 실제 등록 번호를 사용하지 않는다. 기존 샘플을 이번 자료에 넣지 않았으며, 두 합성 서식 계열만으로 실제 회사의 다양한 증빙을 대표한다고 주장하지 않는다.

사람 작성용 Excel과 `ground_truth_dev.json` 및 `ground_truth_test.json`은 자동 추출 결과를 넣지 않은 빈 상태다. Excel의 정답 칸이 실제로 모두 비어 있는지 확인했다. 미확정 JSON으로 정식 측정 명령을 실행하면 종료 코드 2로 중단하고 보고서를 생성하지 않았다. 빈 Excel 가져오기도 거부했으며 사람 정답 JSON과 확정 기록이 바뀌지 않았다. 생성 정보 초안은 별도 파일에 저장했다.

### 파일 확인과 환경 제약

이 단계의 추가 검증은 13개다. 일치한 해석 의문도 필수 확인으로 선정하는지, 실제 사람 확인과 AI 일치 출처 및 집계가 보존되는지, 미완료 검수와 응답 변경을 차단하는지, 표본 오류에서 범위 확대가 필요한지, 전수 확대 후 수정이 가능하고 보고서에 검수 범위를 명시하는지를 독립적인 작은 예제로 확인했다. 전체 백엔드 테스트 141개가 통과했고 기존 경고 555개가 남았다. TypeScript 및 프런트 빌드도 통과했다.

사용자가 Excel의 선택 항목을 원문으로 확인하여 저장하면 dev 정답 확정과 정식 규칙 기준 성능을 측정한다. 이후 로컬 LLM과 근거 검증 및 네 조건의 비교 평가를 진행한다. 이번 단계는 앱 화면이나 디자인을 변경하지 않았다.

## 사람 검수 범위 축소와 확인 방법

2026년 10월 2일 사용자는 검수 부담을 줄이고 무엇을 대조해야 하는지 설명해 달라고 요청했다. 이번 변경은 기존 평가 양식과 직접 연결된 도구·안내에 한정했다. 앱 기능이나 디자인은 수정하지 않았다.

현재 `reconciliation-v3`는 해석·모호함 확인 26칸을 유지하고 나머지 일치 868칸의 10%를 올림한 87칸을 선정한다. 사례와 문서 종류, 계약 전체 검사로 나눈 68개 그룹을 모두 포함하고 그룹 안에서 seed 42로 무작위 선정했다. 총 113칸은 필드확인 60칸과 검수확인 53칸이다. 이전 20% 대조 기록은 보존했다. 26칸과 20%는 과제 필수 수치가 아닌 내부 검토 정책이며, 비율 축소는 일정과 검수 부담을 고려한 선택이다. 표본 비율이나 두 AI의 일치가 전체 정답의 정확도를 보증하지 않는다.

Excel은 사례·문서 순서로 정렬하고 기존 M열을 항목별 확인 방법으로 바꿨다. 원문 공급자 정보와 최종 필드 초안의 대조, 공급가액·세액·표시 합계의 산술 검사, 등록 계약 금액과 청구의 대조를 구분했다. 예를 들어 case_10의 표시 합계 2,201,000원은 추출 정답으로 유지하지만 공급가액 2,000,000원과 세액 200,000원의 합과 다르므로 산술 검사는 FAIL이다. case_09의 참고값은 숫자의 뜻을 확정할 수 없어 REVIEW와 빈 값을 제안한다. 확인·근거·검수자 칸은 사람이 작성하도록 계속 비워 두었다.

정답 가져오기는 새 표본 방식과 목록을 재현하며 현재 버전을 기본값으로 사용한다. 사람 확인이 완료되면 직접 확인 113칸과 AI 일치 채택 781칸을 구분해 기록한다. 현재는 사람 확인과 정답 확정을 실행하지 않았다. 새 선정 방식의 재현성, 총 표본 수와 사례·종류 포함 여부를 작은 독립 예제로 확인했다. 전체 백엔드 테스트 142개와 TypeScript·프런트 빌드가 통과했다. 저장 Excel의 113개 확인·근거 칸과 검수자 칸이 빈 상태이며 원문목록 시트는 이전 값과 동일함을 확인했다. 미확인 양식의 가져오기는 검수자 확인에서 중단했고 dev·test 정답은 계속 미확정이다.

## 사람 검수 완료와 정식 규칙 기준 성능

2026년 10월 2일 검수자 이창헌이 `eval/human_review_page`에서 원문을 보며 113칸을 확인한 결과 JSON을 전달했다. 113칸 모두 확인이며 수정과 보류는 0건이다. 원본 JSON을 `eval/human_reviews/human_review_result_이창헌.json`에 바이트 그대로 보관하고 SHA256 출처 기록을 남겼다. 칸별 확인 시각과 근거도 보존했다. 확인 시각은 같은 날 10:08~10:21 KST이다. 사용자의 직접 검수 기록이며 Codex가 사람을 대신해 확인 표시를 만든 것이 아니다.

원본 `human_review.xlsx`는 보존하고 사본 `human_reviewed.xlsx`의 K·L열에 시트명·행 번호·확인 ID를 일치시켜 반영했다. B12에는 검수자 이창헌을 기록했다. 가져오기 절차로 `ground_truth_dev.json`을 확정하고 정답·Excel·자료 목록·사람 결과 JSON의 해시 및 칸별 확인 시각 출처를 남겼다. 생성 정보 초안과 Claude 응답은 변경하지 않았다.

113칸(해석 26칸 + 일치 항목 10% 표본)은 사람이 원문을 보고 확인했고, 나머지 781칸은 두 AI 초안의 일치로 검증했다. 사람 전수 검수라고 기록하지 않는다. 확인 대상이 아닌 DOCX 모든 페이지의 시각 검증까지 완료했다고 주장하지 않는다.

확정 정답 기준의 규칙 성능은 분류 Macro F1 1.0000, 핵심 필드 정확도 78.34%(264/337), 누락 Recall 1.0000(2/2), 교차검증 Macro F1 0.7530, 문제가 있는 항목에서 잘못된 PASS 0/17이다. FAIL 정답 4건 중 FAIL 검출은 1건이다. 수정 없이 확정되어 초기 예비 수치와 같지만, 이제 확정 정답 기준의 dev 개발 평가다. 별도 test 결과나 실제 회사 서류 성능으로 해석하지 않는다. 결과는 `docs/eval/dev/baseline/`의 JSON·Markdown·CSV에 저장했다.

dev 측정과 정답 가져오기에서는 test 파일 내용을 열지 않도록 자료 해시 확인 범위를 dev로 제한했다. dev/test 서식 분리 여부 등 목록 메타데이터 검사는 유지한다. 최종 `--final` 전에는 test 문서와 정답을 개발·튜닝에 사용하지 않는다.

## 로컬 LLM 보완과 근거 검증 구현

2026년 10월 2일 Ollama 로컬 클라이언트와 보수적인 근거 검증을 추가했다. 설치 qwen3:latest는 8.2B Q4_K_M 약 5.23GB, gemma3:latest는 4.3B Q4_K_M 약 3.34GB이며 RTX 4070 Laptop 8GB 환경에서 비교했다. 약 9.61GB인 gemma4는 제외했다. Ollama 0.35.0의 클라우드 설정을 비활성화하고 실제 재시작 서버 로그의 cloud disabled=true를 확인했다. HTTP loopback와 설치된 허용 모델만 사용하며 문서의 외부 API 전송은 추가하지 않았다. 원문이나 응답 내용을 로그에 출력하지 않는다. 기존 WinOCR 실패 출력도 예외 본문을 빼고 고정 실패 메시지만 남겨 문서 정보가 예외를 통해 출력되지 않게 했다.

최종 프롬프트는 grounded-fields-v3다. 첫 dev 시도에서 상태·근거 문구 누락과 페이지 번호를 줄 번호로 답하는 문제가 나와, 필드 의미와 VALUE/REVIEW 정의를 명시하고 각 원문 줄에 page/line을 함께 붙였다. v2 비교와 버전별 원본 응답도 보관했다. 이는 dev를 사용한 프롬프트 개선이며 test 성능을 확인한 것이 아니다. qwen3와 gemma3의 사전 지정 dev 8문서를 같은 v3로 비교했다. qwen3의 가드 없는 필드 정확도는 46/48(95.83%), 가드를 적용한 LLM만 추출은 36/48(75.00%), 최초 호출 평균은 10.430초였다. gemma3는 각각 37/48(77.08%), 25/48(52.08%), 8.132초였으며 1문서의 형식 오류가 있었다. 가드 적용 정확도, 원본 정확도, 시간 순 기준으로 qwen3를 선택했다. 이 작은 8문서 결과는 모델의 일반적인 우열이나 전체 dev 성능이 아니다. DOCX 페이지 미확인과 잘못된 근거 위치 때문에 실제 값도 거부될 수 있으며, LLM만 가드 결과에는 규칙 보존이 없다.

설정은 읽기 타임아웃 45초·연결 5초·재시도 1회, temperature 0·seed 42·num_ctx 4096·num_predict 1600·keep_alive 5분이며 qwen3는 think=false다. JSON 스키마와 응답 타입을 검사한다. 모델 digest·설정·프롬프트 버전도 저장한다. 최초 로딩과 재시도 시간은 원래 호출시간에 포함한다. 실행법과 한계는 `docs/eval/local_llm_runbook.md`에 기록했다. [Ollama 구조화 출력](https://docs.ollama.com/capabilities/structured-outputs), [클라우드 비활성화](https://docs.ollama.com/faq), [thinking 설정](https://ollama.com/blog/thinking)을 확인했다.

규칙값이 비었거나 원문 후보·당사자·산술과 모순인 필드에만 LLM을 호출한다. 성공한 규칙 필드 전체를 LLM으로 덮어쓰지 않는다. VALUE 제안은 실제 페이지·줄·원문 오프셋, 값의 존재, 필드 라벨, 공급자 구역, 후보 모호성, 형식과 사업자번호 체크섬을 검사한다. 채택·거부 사유는 `analysis.ai_review`와 기존 추출 JSON에 저장해 API에서 제공한다. 원문 존재·위치는 PDF 텍스트와 OCR 문자열을 기준으로 확인하며 이미지의 OCR 오독과 픽셀 좌표 강조는 검증하지 않는다. 모든 AI 채택은 사람 확인 전이며 기존 담당자 추출 확인 API 이후에만 사람 확인 상태를 기록한다. 타임아웃·서버 중단·형식 오류는 규칙값과 실패 코드를 남기고 수동 확인으로 이어진다.

참고값 A/B는 REVIEW로 보류한다. 원문에 잘못 계산된 합계가 있으면 표시값을 보존하고 SOURCE_ARITHMETIC_MISMATCH를 기록한다. 기존 RuleEngine이 산술과 계약 일치를 판정하며 LLM은 PASS/FAIL을 정하지 않는다. DOCX는 실제 페이지를 확인할 렌더러가 없어 VALUE 제안을 PAGE_UNVERIFIED로 거부하고 규칙값을 유지한다. 이 가드가 기존 규칙값까지 검증했거나 모든 의미·OCR 오류를 해결했다고 주장하지 않는다.

Qwen3-8B의 Apache-2.0 라이선스와 상업적 사용·배포 조건은 [공식 LICENSE](https://huggingface.co/Qwen/Qwen3-8B/blob/main/LICENSE)에서 확인했다. Gemma3는 별도의 [이용 약관](https://ai.google.dev/gemma/terms)과 [금지 사용 정책](https://ai.google.dev/gemma/prohibited_use_policy)에 따른다. 상업적 사용도 이 조건을 따라야 하며 배포 시 약관·제한·수정 표시·해당 Notice 조건이 있다. Gemma4 라이선스를 Gemma3에 적용하지 않는다. 모델 가중치는 제출 소스나 커밋에 넣지 않았다.

이번 단계에서도 프런트 화면과 디자인은 변경하지 않았다. AI 근거 표시 화면을 승인받기 전이므로 APP_LLM_ENABLED는 기본 false다. 비교 CLI는 앱 활성화와 별개로 실제 로컬 추출을 실행한다.

## 확정 dev 네 조건 비교 결과

최초 전체 평가에서는 가드가 핵심 필드 79.53%(268/337)만 맞췄다. 거부 121건 중 FIELD_LABEL_OR_VALUE_MISMATCH가 117건이었다. 대부분은 OCR이 콜론을 점으로 읽은 `상호. 값`, `공급가액. 값`을 검증기가 처리하지 못한 문제였다. 점 뒤에 공백이 있는 구분자만 해석하도록 수정했고 원문이나 모델 제안값은 고치지 않았다. 소수점 `.5`를 구분자로 오인하지 않는 회귀 사례도 확인했다. 최초 수치와 근거는 `docs/eval/dev/comparison/initial_guard/`에 보존했다. 후속 가드 버전은 grounding-v2-ocr-separator다.

구분자 수정은 근거 검사뿐 아니라 실패·모순 필드 선정에도 영향을 준다. 따라서 최초 평가와 후속 평가 차이를 순수한 가드 효과라고 주장하지 않는다. 각 최종 실행 안의 ③·④는 같은 모델 응답을 재사용해 가드 효과를 비교한다. 실제 59문서 모두 response_id가 같음을 확인했다. 원래 호출시간을 캐시에서 보존하고 마지막 재실행은 캐시만 읽어 실제 추출 시간을 캐시 속도로 바꾸지 않았다.

| ④ 규칙+LLM 가드 있음 | 311/337 | 92.28% | 97.33% | 0.9869 | 0/17 | 29 | 2.164초 |

④는 규칙 기준보다 핵심 필드 정확도 13.95%p, 검수 Macro F1 0.2339가 높아졌다. 같은 제안에 가드만 추가한 ③→④에서는 핵심 필드 정확도가 6.82%p 낮아졌다. 가드가 모든 지표를 개선한 것은 아니다. 잘못된 PASS는 네 조건 모두 0/17이며 감소를 입증하지 못했다. 이 작은 표본에서의 0건으로 안전성을 보증하지 않는다. FAIL 정답 4건 중 규칙은 1건을 찾았고 가드 포함 LLM 보완은 4건을 찾았다. 분류 Macro F1은 공통 규칙 분류기를 쓴 59문서 모두 1.0000, 누락 Recall은 모든 조건에서 2/2였다. 모델 기반 분류 성능이라고 소개하지 않는다.

가드 거부는 29제안이다. PAGE_UNVERIFIED 15, EVIDENCE_NOT_FOUND 11, FIELD_LABEL_OR_VALUE_MISMATCH 21, WRONG_PARTY 3, VALUE_NOT_IN_QUOTE 4, UNSUPPORTED_ABSTENTION 1이며 한 제안에 여러 사유가 있을 수 있다. 확정 정답을 사용한 사후 대조에서는 거부된 값 또는 보류 27개가 정답과 일치했고 2개는 불일치했다. 이는 위치·라벨·당사자 근거까지 올바르다는 뜻은 아니다. 값이 맞아도 근거가 잘못되면 거부하는 정책 때문에 처리율과 정확도 손실이 남는다. 정답은 이 사후 분석에만 썼으며 실제 가드나 LLM 프롬프트에는 넣지 않았다. 세부 결과는 `guard_audit.json`에 있다.

LLM만은 핵심 7필드 추출을 모두 LLM으로 수행하는 평가 조건이다. 분류와 최종 판정은 모든 조건에서 같은 규칙을 사용한다. 실패·모순 필드 보완은 59문서 중 28문서에서 호출했고, 선택 모델의 최종 네 조건 실행에는 LLM 실패 문서가 없었다. ABSENT 정답 76칸의 거짓 추출은 네 조건 모두 0건이다. 필드 정확도는 VALUE 333칸과 REVIEW 4칸을 분모로 유지하며, 거부·보류도 평가에서 빼지 않았다.

검수 정확도는 정답 또는 출력에서 적용되는 항목의 합집합이다. 양쪽 N/A는 제외하고 누락·추가 출력을 오답으로 세므로 조건별 분모는 규칙 84, LLM만 74, 가드 없음 74, 가드 있음 75다. 결과를 쉽게 맞추는 N/A 300여 건을 정확도 분모에 넣지 않았다. 문서 평균 시간은 공통 분류·OCR·페이지 확보+최초 실제 LLM 호출+해당 가드이며 규칙 검수와 사람 확인 시간은 제외한다. 캐시 실행 시간과 문서별 근거·실패·채택 여부도 별도 JSON에 저장했다.

사람 확인 113칸(해석 26칸+일치 항목 10% 표본 87칸), 나머지 781칸은 두 AI 초안 일치 검증이라는 범위는 그대로다. dev 정답 SHA256은 6361b13bd820f40cea38edf5df66da1714d1b0b1fb045763c3795d28d1d84f5b이며 평가 전후 동일하다. 이 결과는 확정 정답을 사용한 dev 개발 평가이며 예비 정답 수치 또는 별도 test 최종 성능이 아니다. 기존 preliminary 보고서는 보존했다. 발표의 최종 성능은 독립 test 정답 확정 후 측정해야 한다.

결과 JSON·Markdown·CSV, 모델 선택, 원본 LLM 응답 캐시, 근거 기록은 `docs/eval/dev/comparison/`에 있다. test 최종 실행은 --final, dev에서 선택한 모델 이름·digest·프롬프트·가드 버전 일치와 확정 정답을 요구한다. 이 작업에서 실제 test를 실행하거나 문서·정답을 열지는 않았다.

전체 백엔드 테스트 172개가 통과했다. 기존 라이브러리·UTC 사용의 경고 597개는 남아 있으며 이번 기능의 정확도 수치와 별개다. 공급받는자 번호, 다른 필드 라벨, 지어낸 값, 모호한 금액, 원문 산술 오류 보존, 페이지 미확인, 원격 모델·클라우드 설정 차단, 타임아웃 재시도, 캐시 변조, 동일 응답 가드 비교, 불필요한 LLM 호출 생략과 AI 근거 저장·사람 확인 이후 보존을 확인했다. ## 가드 v3: 맞는 값의 거부 완화와 처리율 감사

2026년 10월 2일 사용자 요청에 따라 가드를 유지하고 dev에서만 거부 원인을 분석했다. **가드 v3는 dev 감사 결과로 조정함.** 버전은 `grounding-v3-dev-audit`이다. 이전 v2 수치와 원본 응답은 `docs/eval/dev/comparison/`에 그대로 남겼고 새 결과는 `docs/eval/dev/guard_v3/`에 JSON·Markdown·CSV로 저장했다. 실제 test 문서와 정답은 열지 않았다.

`PAGE_UNVERIFIED` 15건을 모두 DOCX로 분류했던 해석은 바로잡았다. 실제로는 DOCX 4건과 PDF·PNG 금액 범위 제안의 위치·문구 누락 11건이다. 정답에 맞았던 거부 27건은 다음과 같이 나뉜다. 이 원인별 감사와 기존 오답의 회귀 확인에는 확정 dev 정답을 사용했으며 운영 가드나 프롬프트에는 정답을 전달하지 않았다.

| 정답 일치 거부 원인 | 건수 | 변경과 남은 제한 |
| --- | ---: | --- |
| DOCX 물리 페이지 요구 | 4 | 실제 문단 번호 또는 표·행·셀·문단 위치를 확인한 뒤 채택 |

**DOCX는 페이지 배치는 미확인, 글자 근거는 확인.** 기존 평문 추출을 실제 DOCX 문단·표 셀 내용과 다시 대조하여 위치를 저장한다. 문자열이 다르거나 위치가 확인되지 않으면 `DOCX_LOCATION_UNVERIFIED`로 거부한다. `page=null`, `page_layout_verified=false`, 실제 문단 또는 표·행·셀·문단 위치와 문자 오프셋을 저장한다. 임의로 페이지 1을 붙이거나 Word 페이지 배치를 검증했다고 기록하지 않는다.

줄 번호 ±1 허용은 원문 인용문이 정확히 존재하고 동일 필드 라벨·동일 값·동일 당사자가 확인된 경우에만 적용하며 실제 위치와 원래 제안을 함께 남긴다. 이번 27건의 실제 주된 원인을 줄 번호 오류로 바꾸어 설명하지 않는다. 2줄 차이, 잘못된 페이지, 다른 라벨, 당사자 경계를 넘어선 이동은 허용하지 않는 회귀 사례를 확인했다. 금액 범위에서 모델이 낸 잘못된 인용문은 새 근거로 대체하지 않는다. 참고값 A/B에 FULL/PARTIAL 또는 계산 금액을 부여하지 않는다.

기존 오답 2건은 실제 저장 응답으로 다시 확인했다. 10706 검수확인서의 금액 범위를 ABSENT로 답한 제안은 `UNSUPPORTED_ABSTENTION`, 10902 견적서에 근거 없는 PARTIAL을 답한 제안은 `FIELD_LABEL_OR_VALUE_MISMATCH`로 계속 거부된다. 기존에 거부한 오답을 새로 채택한 건수는 0이다. 참고값 A/B를 ABSENT로 답한 공급가액·세액·합계 3건도 새로 `AMBIGUOUS_UNLABELED_AMOUNT`로 거부한다. 값이 없다는 답과 의미를 확정할 수 없다는 답을 구분하기 위한 변경이다.

### 같은 LLM 응답으로 재측정한 확정 dev 결과

기존 59문서의 원문, 요청 80필드, 프롬프트 v3, qwen3 모델 digest와 설정, 원본 LLM 응답을 고정했다. 캐시가 없거나 입력·응답 해시가 다르면 새 호출 없이 중단한다. ③·④의 문서별 response_id도 모두 같고, 이번 59문서에서 새 가드의 실제 호출 대상 선정도 기존과 일치했다. 재생 중 새 LLM 추출은 호출하지 않았다. 최초 호출시간과 기존 OCR·규칙 시간을 보존하고 가드 시간만 다시 측정했다. 모델은 v2 가드의 기존 dev 8문서 비교로 선택한 qwen3를 유지했으며 v3에서 다시 고르지 않았다.

### 버전 고정과 남은 최종 평가

`docs/eval/dev/guard_v3/release_lock.json`에 가드·프롬프트 버전, qwen3 모델 digest, LLM 설정, 관련 추출·검수·평가 코드의 SHA256과 dev 정답·자료 목록 해시를 고정한다. 모델 설정은 기존 temperature 0·seed 42·45초 타임아웃·재시도 1회·num_ctx 4096·num_predict 1600으로 유지한다. 소스 코드 해시는 CRLF를 LF로 정규화하여 Git 줄바꿈 변환과 실제 코드 변경을 구분한다. 설정과 실제 설치 모델이 다르거나 코드가 바뀌면 최종 평가를 차단한다.

실제 test 문서·정답을 열거나 최종 평가를 실행하지 않았다. 독립 test 정답의 확인·확정 후 고정 버전으로 `--final`을 한 번 실행한다. 최종 시도는 자료 폴더에 `final_evaluation_attempt.json`을 독점 생성하며 출력 폴더를 바꾸어도 다시 실행할 수 없다. 버전·확정 정답 확인 뒤 test 문서를 처음 열기 전에 시도를 예약한다. 실패·중단도 기록을 남기고 자동 재실행하지 않는다. 실제 최종 시도 기록은 이번에 생성하지 않았다.

백엔드 전체 테스트 191개와 TypeScript·Vite 프런트 빌드(1,908모듈)가 통과했다. 기존 경고 597개는 남아 있다. 새 회귀 확인에는 DOCX 문단·표·병합 셀·다중 줄 위치, 원문 변경 시 거부, 공급받는자 거부, ±1 안전 범위, 숫자 공백과 구분 기호, 모호 금액의 ABSENT 거부, 기존 오답 유형, 기계 검증과 사람 승인의 구분, 캐시 재생, 버전 변경 차단 및 최종 재실행 차단을 포함했다. 로컬 커밋만 남기며 push·PR은 하지 않는다.

## 통합 실행기와 운영·유지보수 안내

여러 실행 파일 때문에 시작 방법이 어렵다는 요청에 따라 평소 실행 입구를 `C-Pilot.exe` 하나로 묶었다. 서버가 준비되면 브라우저를 열고, 이미 같은 서버가 있으면 재사용한다. 실행 창에서 M을 입력하면 최초 환경 준비, 상태 점검, 업무함 준비, 포트·자료·백업·사내망 설정, 백업, 새 폴더 복원, 선택적 예약 작업 등록, 서버 종료를 관리한다. 상태 안내는 한국어로 제공한다. 회사·직원·필수서류 설정은 기존 앱에서 관리하며 화면과 디자인은 변경하지 않았다.

EXE는 Windows .NET Framework로 빌드하는 작은 실행 입구이며 Python·앱·모델을 포함한 독립 설치형 프로그램은 아니다. 소스는 `tools/launcher/Program.cs`, 빌드는 `tools/build_launcher.ps1`, 실행 로직은 `backend/pilot_launcher.py`로 분리했다. 새로 받은 Git 소스는 처음 한 번 `start_pilot.bat`을 실행하면 EXE를 만들고, 이후에는 EXE를 사용한다. 생성 EXE와 실행 설정·로그·프로세스 기록은 Git에서 제외한다. 새 PC의 최초 환경 준비에는 Python 3.12와 Node.js·npm 및 패키지 다운로드가 필요하다. 기존 개발·고급 운영 스크립트는 보존하되 README의 기본 경로는 통합 실행기로 정리했다.

실행·관리 작업은 OS 파일 잠금으로 중복을 막는다. 다른 프로그램이 포트를 사용하면 접속·종료하지 않는다. 서버 재사용은 실행 식별자와 PID를 대조하고, 종료는 실제 Windows 프로세스의 생성 시각·실행 경로를 같은 프로세스 핸들로 확인한 뒤 적용한다. `/health`는 이 실행기를 사용할 때만 고유 식별자와 PID를 추가하며 자료 경로나 계정 정보를 노출하지 않는다. 통합 실행기는 로컬 HTTP·단일 서버·국세청 조회 비활성·LLM 비활성을 유지한다. LLM이나 가드·프롬프트의 평가 고정 코드는 바꾸지 않았다.

백업과 복원은 기존 업무함 관리 도구를 재사용한다. 복원은 서버가 꺼져 있고 존재하지 않는 새 폴더에서만 진행한다. 성공 후 자료 설정을 전환하며 실패하면 현재 설정은 유지한다. 기존 자료는 자동 삭제하지 않는다. 백업은 초기 계정 비밀번호 안내 파일을 제외하고 복원 후 로그인 세션을 만료한다. 자동 실행·백업은 사용자가 메뉴에서 선택하면 같은 설정 파일을 사용하는 예약 작업으로 등록한다. 이번 검증에서는 실제 고객 설정·업무함·Windows 예약 작업을 변경하지 않았다. 예약 작업은 구문 검증했으며 실제 등록·예약 시각 실행을 검증했다고 주장하지 않는다.

별도 임시 자료 폴더에서 실제 EXE로 빈 업무함 준비 → 서버 실행 → 같은 서버 재사용 → 백업 → 종료 → 새 폴더 복원 → 재실행 → 종료를 확인했다. 백업의 DB 포함·초기 비밀번호 파일 제외, 복원 설정 전환, 서버 준비와 최종 종료도 확인했다. 검증 기록은 `docs/operations/launcher_smoke.json`에 보관했다. 첫 EXE 시험에서 Windows 환경 변수의 `Path`·`PATH` 중복 문제가 발견되어 환경 변수 사전을 재구성하지 않고 Python UTF-8 실행 옵션을 전달하도록 수정했다. 한글·공백이 있는 실제 프로젝트 경로와 BAT 초기 실행 경로에서도 정상 동작했다.

백엔드 전체 207개 테스트(597개 기존 경고)와 TypeScript·Vite 빌드(1,908모듈)가 통과했다. 실행기 16개 확인은 잘못된 설정, 자료 안의 백업 경로 거부, 동시 실행 잠금, 다른 서버 응답·PID 재사용 거부, 실패한 복원에서 설정 보존, 기존 DB 덮어쓰기 거부, 준비 작업 실패 중단, 외부 조회·LLM 비활성, 건강 확인 응답의 정보 범위를 다룬다. PowerShell 네 파일의 구문 검사와 EXE 빌드도 통과했다.

`docs/operations/run_guide.md`에 로그인·Caps Lock·퇴사 계정 비활성화·다른 PC 접속·백업·사내망 유지보수를 정리했다. 현재 비밀번호 해시·세션 폐기·권한 확인은 기존 구현이며 Caps Lock은 입력 편의 기능이다. 2차 인증, HTTPS 자동 구성, 단독 설치형 배포, 오프라인 설치 묶음, 서명한 자동 업데이트·DB 버전 이주·라이선스 보호는 미구현 범위다. 실행 파일 포장은 복제나 고객의 AI 수정·직접 유지보수를 완전히 막지 못하며 현재 EXE는 Python 소스를 숨기지 않는다. 판매 시 공식 버전 지원·고객 수정 버전 점검·업데이트 범위를 합의하는 방향을 설명했고 복제 감시·외부 자동 연락 기능은 추가하지 않았다. 원격 지원은 회사가 승인한 접속 방식으로, 차단된 망은 승인된 업데이트 반입 또는 방문으로 진행하는 운영 선택지를 기록했다.

dev 정답·생성 초안·자료 목록 해시와 가드 v3 고정 코드는 그대로임을 확인했다. test 문서와 정답은 열지 않았고 최종 평가 시도 파일도 생성하지 않았다. 기존 dev 성능 수치를 새 성능 개선으로 다시 주장하지 않는다. 다음 작업은 test 정답 확인·확정과 고정 버전의 1회 최종 평가, 승인받은 근거 화면, 제출 문서·시연 준비다. 판매용 인증·배포·유지보수 제품화는 별도 범위로 둔다. 이번 변경은 로컬 커밋만 남기고 push·PR은 하지 않는다.
