# 맡긴 일을 수정한 뒤 완료하지 못하는 오류 수정

견적서 금액 확인을 맡은 사람이 값을 고치면 계약 자료 revision/fingerprint가 바뀐다. 기존 API는 배정 이후 변경된 업무를 시작·완료 모두 차단해, 실제로 일을 처리한 뒤 COMPLETE가 409가 되는 문제가 있었다.

## 변경

- COMPLETE는 자료가 바뀌어 is_stale=true여도 허용한다. 문서 업무는 같은 계약의 현재본이어야 하며 이전본·삭제된 문서는 409다. 계약 단위 업무도 완료할 수 있다.
- START는 기존대로 stale이면 차단한다. 현재 담당자·대표·관리자의 완료 권한, 필수 처리 메모, assignment_revision 충돌 검사, 완료·취소 업무 재변경 차단은 유지한다.
- 감사 이벤트의 completion_context에 배정 당시와 완료 당시 revision/fingerprint 및 was_stale을 남긴다. 배정 기준은 그대로 보존한다. 따라서 완료된 업무도 is_stale=true일 수 있으며 완료 실패를 뜻하지 않는다.
- 업무 완료는 계약 검수 결과나 대표 결재를 바꾸지 않는다. DB 스키마·요청 형식 변경은 없다. [API 인계 문서](../../api/frontend_handoff.md#사내-담당자에게-맡기기-2026-10-03)에 연결 기준과 감사 필드를 기록했다.

## 검증

기존 코드에서 실제 API의 ‘배정 → 금액 수정 → 완료’ 네 경로(미시작/진행 중 문서 업무, 계약 단위 업무, 대표 완료)가 모두 409로 실패함을 재현했다. 같은 테스트로 수정 후 성공을 확인했다. 완료 전후 계약 revision/fingerprint·결재 상태가 같고, 업무 목록에서 닫힌 항목이 제외되는 것도 확인했다.

잘못된 담당자의 완료, 빈 메모, 오래된 assignment_revision, 재발행된 이전본, 삭제된 문서, 이미 종료된 업무도 검사했다. 맡기기·필드 수정·문서 버전·ZIP 이력의 **관련 테스트 29개가 모두 통과했다**(새 회귀 사례 5개 포함). 기존 라이브러리·datetime 사용 중단 예고 경고는 남아 있다. 운영 DB와 동결된 모델·프롬프트·가드·평가 자료는 변경하지 않았다.

frontend는 수정하거나 병합하지 않았다. Claude가 e6fb91c에서 준비한 버튼의 백엔드 차단 사유를 해결한 변경이며, 브라우저 통합 확인은 10/5 병합 후 별도 진행한다. 적용하려면 이 커밋의 백엔드로 재시작해야 한다. 로컬 커밋만 하고 push·PR은 하지 않는다.
