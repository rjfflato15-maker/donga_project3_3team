# 동결 뒤 test3 검출 성능 평가 계획

**계획만 작성했다. test3 문서·정답·예측은 아직 만들지 않는다.** test2에는 FAIL·MISSING 정답이 없어 불일치·누락 검출 성능을 측정하지 못했다. 도장 가림 등 판독 과제와 실제 검수 문제 검출을 분리해 보완한다.

## 고정과 표본

기능 동결 뒤 평가할 코드·모델·프롬프트·가드·업무 기준을 먼저 고정한다. 새 문서 계열과 가상 값으로 구성하고 개발자가 test3 결과를 보고 튜닝하지 않는다. 기존 test·test2를 복사해 최종 성능처럼 보고하지 않는다. 수정이 필요하면 개발용 자료에서 하고 다음 버전·다음 평가로 분리한다.

첫 계획은 계약 24건(주된 목표 상태별 6건)이다. 비용에 맞춰 실행 전에 확정하며, 6건씩은 탐색 표본이라 좁은 신뢰구간이나 안정적 검출률을 보장하지 않는다. 계약마다 주된 문제를 하나로 제한하되 최종 라벨은 검사 항목별로 기록한다. 다른 정상 검사까지 계약 전체 FAIL로 바꾸지 않는다.

| 주된 상태 | 계획 건수 | 포함할 상황 |
| --- | --- | --- |
| PASS | 6 | 정상, 공급가액 기준, 분할 지급 합산 등 합의된 정상 처리 |
| FAIL | 6 | 공급자 번호 불일치 2, 계약 대비 금액 불일치 2, 공급가액·세액·합계 산술 불일치 2 |
| MISSING | 6 | 필수 서류 한 종류가 실제로 빠짐. 종류를 고르게 배분하고 읽기 실패와 구분 |
| REVIEW | 6 | 가림·흐림으로 값 확인 불가, 여러 후보·공급자 구역 모호, 적용 범위를 확정할 수 없는 금액 |

FAIL에는 원문에서 읽을 수 있는 실제 불일치가 있어야 한다. 단순 OCR 실패를 FAIL 검출로 세지 않는다. N/A는 미적용 상태로 분리한다. NTS는 disabled이며 BUSINESS_STATUS REVIEW는 안내성 고정 항목으로 따로 집계한다. 계좌번호 검증은 현재 평가 필드가 아니므로 이 계획에 넣으려면 필드·검사·정답 기준을 실행 전에 별도로 합의한다.

## 정답과 측정

생성 설계 초안과 독립 원문 판독을 대조한다. 불일치·해석 및 무작위 일치 표본을 사람이 확인하고 직접 라벨 확인·원문 사실 확인·AI 일치·사후 기준 적용을 구별한다. 중립 질문으로 묻고 자료·정답·코드 해시를 보존한다. 표본·지표·제외 기준은 실행 전에 고정한다.

규칙만 / LLM만 / 규칙+LLM 가드 없음 / 규칙+LLM 가드 있음의 네 조건을 사용한다. 두 hybrid 조건은 같은 저장 LLM 응답을 공유한다. 버전당 추론 한 번과 저장 예측의 채점을 분리한다.

- FAIL·MISSING 각각의 TP/FN/FP, Recall·Precision·F1과 분모. 분모가 0이면 0%가 아니라 미측정.
- 실제 문제를 PASS로 표시한 수, N/A→PASS, 실패를 REVIEW로 넘긴 수를 따로 제시한다. PASS를 피했다고 FAIL 검출 성공으로 세지 않는다.
- 필드 오류를 틀린 값 표시 / 빈칸·확인 필요로 나누고 금액·사업자번호를 별도 보고한다. 칸별 확인 안내 여부도 확인한다.
- 사람 직접 라벨 확인 / AI 일치 / 사후 기준 적용별 필드 정확도, 가드 채택 값 정확도와 확인 이관 비율.
- 계약 단위 성공률·처리 시간과 신뢰구간을 함께 보고한다. 계약 안의 칸 수를 독립 표본 수로 과장하지 않는다. 실제 업무시간 절감은 별도 사용자 시험에서 측정한다.

test2 결과와 병렬로 남기며 test3가 기존 실패·한계를 지우는 자료가 되지 않게 한다.
