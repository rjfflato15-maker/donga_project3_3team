## Claude가 먼저 보완할 디자인 규칙

### 후속 사용자 선택: 접고 펼치는 왼쪽 사이드바

사용자가 상단 앱 메뉴보다 Codex처럼 토글하는 왼쪽 사이드바를 선호한다고 명시했다. **앱 전체 메뉴는 왼쪽 사이드바로 정한다.** 앞선 상단 메뉴안은 가능한 대안에 대한 검토였으며 최종 선택으로 유지하지 않는다. 아래 내용은 다음 시안의 요구이며 아직 frontend에 구현하지 않았다.

- PC: 기본 펼침에서 아이콘과 메뉴 이름을 함께 표시하고, 선택한 메뉴를 분명히 표시한다. 토글로 접으면 본문이 넓어지며 다시 여는 버튼은 항상 접근할 수 있어야 한다. 접고 펼칠 때 현재 계약·탭·입력 내용을 유지한다.
- 본문 상단: 현재 위치/계약 제목과 계정 등 보조 정보에 사용한다. 같은 앱 전체 메뉴를 상단에도 반복하지 않는다.
- 계약 안의 ‘서류 / 요청 내역 / 결재 / 처리 기록’ 탭과 상태 필터는 본문에 남긴다. 특정 계약의 단계나 값 수정 행동을 앱 전체 메뉴로 옮기지 않는다.
- 모바일: 사이드바를 상시 표시하지 않고 메뉴 버튼으로 여는 겹침 패널로 바꾼다. 메뉴 선택·닫기·Esc 등으로 닫히고 포커스가 적절히 복귀하도록 설계한다. 닫혀 있을 때 본문은 화면 전체 폭을 쓴다.
- 다음 시안에서 같은 계약의 업무함·상세·원문 대조를 펼침/접힘으로 비교하고, 모바일 업무함·대표 결재·원문 확인도 별도로 보여 준다. 현재 PC 고정 폭/2열 화면을 단순히 축소한 것을 모바일 완료로 보지 않는다.

### 공통 화면 보완

1. **구조는 유지하고 설명의 기준을 바꾼다.** 중복 설명은 줄이되 필수 입력 조건, 비활성 이유, 복사/발송/기록의 차이는 해당 행동 옆에 한 줄로 둔다. ⓘ는 마우스 hover만으로 접근하지 않고 키보드·클릭으로도 열리게 한다.
2. **좁은 표의 가독성을 보완한다.** 본문 14px, 행 높이 38~42px 정도를 비교안으로 확인한다. 무조건 모든 표를 키우기보다 W3의 확인 열과 긴 이름·사유의 줄바꿈부터 고친다. 현재 구조를 다시 많은 카드로 나누지는 않는다.
3. **용어는 실제 사용자 기준으로 정한다.** 현재 담당자에게는 ‘결재 요청’이 ‘상신’보다 바로 이해될 수 있다. ‘승인·반려’는 유지할 수 있다. 더존 같은 제품의 관습만으로 익숙함을 가정하지 않는다.
4. **상태 탭의 수보다 기준을 먼저 정한다.** 6개 탭이 반드시 잘못된 것은 아니다. 내 처리는 역할/차례 필터이고 회신 대기·반려 등은 상태 필터라 계약이 중복될 수 있다. 제목 건수·탭 건수·행 행동이 같은 서버 기준을 따라야 한다.

## README의 API 설명 검증

### 1. 반려 사유·결재 의견 이력

- 대표 확인/반려는 activity의 `REPRESENTATIVE_CONFIRMED` / `REPRESENTATIVE_RETURNED`에 `note`, `review_id`, revision/fingerprint가 기록되므로 의견 이력을 표시할 수 있다.
- 담당 검토의 `APPROVAL_FIRST_STAGE` activity에는 revision만 있다. 담당 검토 의견은 `GET /api/pilot/contracts/{id}/approvals`의 history에서 가져온다. activity만으로 모든 결재 의견이 나온다고 쓰지 않는다.
- 현재 확인/승인에도 비어 있지 않은 note가 필요하다. FAIL/REVIEW가 남으면 `acknowledge_unverified`와 10자 이상 note가 필요하다. 따라서 W6의 ‘반려 시 필수’ 표기와 ‘국세청 진위 미조회 확인’만으로 모든 미확인 사항을 확인했다는 의미를 대신하지 않는다.
- note를 표시할 때 현행 가림 규칙을 유지한다. 승인/검토 기준 revision이 달라지면 이전 동의를 재사용하지 않는다.

근거: `backend/app/api/pilot.py`, `backend/app/api/workflow.py`, `backend/app/services/activity_service.py`.

### 2. 고친 본과 요청 항목의 연결

현재 기능으로 ‘REISSUE 업로드 → 현재 본 검토 → 요청 항목 RECEIVED 기록’은 가능하다. 그러나 요청 항목의 `document_id`는 요청 당시 서류이며, 수령 처리에는 새로 받은 문서 ID/버전을 저장하는 별도 필드가 없다. 논리 문서 ID로 현재 본을 찾는 화면 연결과 ‘어느 수령본으로 어떤 요청을 해결했는지’의 영구 기록은 구분한다.

W3U처럼 업로드와 받음 기록을 한 동작으로 제공하려면 두 호출의 일부 성공을 표시하고 재시도 시 중복 업로드를 막거나, 명시적인 수령본 연결 API를 별도로 설계한다. 현재 서버에 원자적 결합 저장이 있다고 표현하지 않는다.

근거: `backend/app/db/models.py`의 `RequestBundleItem`, `backend/app/services/request_bundle_service.py`의 `resolve_items`.

### 3. 값별 확인자·시각

**이미 제공된다.** 이름 목록인 `human_confirmed_fields`만 보지 말고 provenance의 `fields[field].human_confirmation`을 사용한다.

```json
{
  "actor_name": "담당자 표시 이름",
  "at": "기록된 ISO 시각",
  "value": 3410000,
  "method": "EXPLICIT_CONFIRMATION"
}
```

`CHANGED_VALUE`는 값을 바꾼 확인이고 `EXPLICIT_CONFIRMATION`은 현재 값 그대로 확인한 기록이다. 원래 읽은 출처는 `original_source`로 구분한다. ‘원문과 같음’을 눌렀다는 이유만으로 규칙/AI 원래 출처를 모두 사람 추출로 바꾸지 않는다. 이전 자료에 확인 증거가 없으면 확인자·시각을 만들지 않는다. 시간 표시는 한국 시간으로 바꾸고 값 가림을 유지한다.

근거: `backend/app/services/field_confirmation_service.py`, `backend/app/services/review_context_service.py`.

### 4. 추가로 바로잡을 구현 범위

- SMALL_BUSINESS는 대표 최종 확인 1단계, MID_SIZED는 담당 검토→대표 2단계다. SMALL_BUSINESS의 ‘기안’ 도장 칸을 실제 담당자 승인 완료라고 채우지 않는다. 명시적인 ‘결재 요청’ 상태/사건은 현행 첫 단계 승인과 같지 않다.
- 첫 결재라면 ‘지난 결재 이후 변경’을 임의로 만들지 않는다. 실제 이전 결재/반려 기록과 기준 본이 있을 때 해당 구간을 표시한다.
- W3의 ‘품목’은 현재 `AnalysisFields`에 없는 예시 필드다. 현행 필드만 표시하거나 후속 기능으로 표시한다.
- 요청 작성의 연락처와 문서번호 형식은 실제 저장 데이터/번호 체계가 있는지 구분한다. 시안의 예시를 운영 사실로 채우지 않는다.
- 3~5명 결재선은 후속 설계다. 현재 최대 2단계 제약과 별도로 단계 ID·결재자·차례·승인/반려 상태의 규칙을 먼저 정한다.
- 비교 페이지의 ‘기능은 같고 화면만 다릅니다’는 결재 상신·추가 필드 같은 제안이 포함된 범위에는 맞지 않는다. 표시 개편과 후속 제안을 구분하고 동일 계약·상황끼리 비교한다. 정적 이미지 선호도는 실제 업무 완료 시간과 다르다.
