# ERP 업무 화면 기준 UI·UX·AX 조사 — 2026-10-06

사용자의 최신 우선순위는 UI·UX·AX다. 결재자 확장이나 추가 기능 구현보다 화면의 공통 설계와 상세 사용 흐름을 먼저 정리한다. 기존 [결재·요청 연구](approval-ui-references-2026-10-06.md)는 기능별 참고 자료로 남기고, 이 문서를 전체 화면 설계 기준으로 우선한다.

AX는 이 앱 맥락에서 AI가 읽은 값·근거·불확실성을 사람이 확인하고 수정하는 경험으로 해석했다. 접근성은 별도로 함께 다룬다. 연구 대상은 담당자·결재자의 데스크톱 업무 화면이며, 결재자가 1·3·5명일 때 읽는 방식까지 고려한다.

## 먼저 합의할 공통 설계 기준

### UI: 화면의 모양과 정보 위계

- **공통 화면 틀:** 내비게이션 → 계약/업무 대상 헤더 → 관련 탭/필터 → 작업 본문 → 행동/결과. 작업이 바뀌어도 계약 이름·금액·상태의 위치가 안정적이어야 한다.
- **글자:** 화면 제목, 영역 제목, 값, 보조 설명의 크기·굵기를 정한다. 긴 설명을 작은 글씨로 한곳에 모으지 않는다. 금액은 숫자/단위/금액 기준을 함께 읽을 수 있게 한다.
- **공간:** 표·폼·읽기 영역의 여백과 행 높이를 정한다. 상태 하나를 알리기 위한 카드와 긴 본문을 담는 영역은 같은 크기/테두리로 강조하지 않는다.
- **색:** 현재 선택/주 행동, 정상, 남은 확인, 오류, AI 출처의 의미를 정한다. 색과 글자를 함께 사용하며 전체 테두리·버튼·상태 배지의 강조가 경쟁하지 않게 한다.
- **행동:** 페이지 전체 행동, 선택한 행 행동, 필드 수정 행동을 구분한다. 각 작업 영역에 주 행동 하나를 정하고 나머지는 보조로 둔다.
- **일관성:** 등록·원문 대조·결재·요청에서 같은 입력칸/닫기/취소/저장·오류/성공 안내를 사용한다.

색상·글꼴·모서리의 최종값은 아직 선택하지 않았다. 공식 참고를 바탕으로 한 시각 방향을 검토한 다음 코드 토큰을 정한다.

### UX: 업무를 이해하고 이어가는 방식

목록은 ‘내가 지금 처리할 것’을 중심으로, 계약 상세는 ‘이번 계약의 상황과 근거’를 중심으로, 대조 화면은 ‘지금 확인할 값’을 중심으로 설계한다. 같은 데이터라도 화면의 과제에 따라 필요한 우선순위가 다르다.

묶음 요청은 ‘대상·항목·사유 → 보낼 문구 → 실제 요청 후 기록’이다. 결재 요청은 ‘대상 자료·핵심 변경 → 검토자·순서 → 최종 미리보기’다. 공통 창 틀을 사용하되 발송/복사/기록/결재 제출의 의미를 합치지 않는다.

결재자가 3~5명이면 이름·직무·현재 차례·완료/대기·의견을 읽을 수 있는 목록이 필요하다. 인원 수와 결재 단계 수, 같은 단계의 전원/한 명 승인 규칙을 구분한다. 화면 시안은 1·3·5명으로 확인하고 실제 N단계 지원은 후속 구현 범위로 명시한다.

### AX: AI 결과에서 사람 판단까지

작업의 최소 단위는 ‘현재 값 한 칸’이다. 해당 칸에서 다음을 읽고 행동할 수 있어야 한다.

1. 지금 저장된 값과 계약 검사 기준이 무엇인지.
2. 규칙 추출/AI 보완/사람 수정·확인 중 어떤 기록이 있는지.
3. 원문의 어느 곳을 근거로 삼았는지. 좌표가 없으면 쪽/줄/인용만 사용한다.
4. 원문을 잘못 읽었으면 값을 수정하고, 원문 자체가 계약 기준과 다르면 정정 서류를 요청할 수 있는지.
5. 저장한 뒤 무엇이 다시 검사되고 기존 확인/결재에 어떤 변화가 생겼는지.

‘근거 있음’, ‘자동 검사 일치’, ‘사람 원문 확인 완료’는 서로 다른 상태다. 모두 같은 초록 정상 표시로 묶지 않는다. 근거를 여러 곳에서 찾았다는 사실과 여러 값이 서로 충돌한다는 사실도 구분한다. 현재 데이터가 없는 확신 점수·확인자·시간은 채워 넣지 않는다.

채팅 입력 없이도 현재 서류/값을 이해하고 확인할 수 있는 경험이 우선이다. AI가 실제로 준비한 요청 초안/검토 항목을 현재 업무에 연결하고, 결과가 적용됐는지 아직 미리보기인지 표시한다. 코드 템플릿으로 만든 문구를 LLM 생성물로 표시하지 않는다.

### 접근성: 시안 뒤 검증할 것

동일 역할의 버튼 크기·초점 표시, 실제 label과 오류의 연결, 색 외 상태 표현, Tab 순서, 모달 초점/닫기/복귀, 확대 시 재배치, 긴 한국어 줄바꿈을 확인한다. 정적 HTML 캡처에서 대비나 접근성 준수 전체를 인증하지 않는다.

## 상세 흐름과 Claude 전달 범위

[상세 플로우·상태표](../ux/contract_review_detailed_flow_20261006.md)에 원문 검토, 묶음 요청/부분 회신, 결재/재결재의 분기와 복귀를 정리했다. 현재 기능과 제안하는 화면/후속 기능을 구분한다.

Claude에게 필요한 다음 산출물은 다음 순서다.

1. 공통 화면 틀/글자/간격/표/폼/버튼/상태·AI 출처 표현의 디자인 기준.
2. 상세 플로우의 화면·클릭·입력·판단·취소·오류·복귀가 연결된 다이어그램과 화면 ID.
3. 대표 화면 3종의 시각 방향: 업무 목록, 계약 검토/원문 대조, 요청·결재. 긴 내용·부분 회신·반려·3~5명 차례 상태도 동일한 틀에 적용.
4. 선택한 방향의 클릭 시안. 기본 흐름만 누르는 전시물이 아니라 수정/취소/복귀/오류 후 재시도를 확인할 수 있어야 한다.

Codex는 기존 데이터 의미와 시안에 쓰는 사실의 연결을 검토한다. 이 단계에서 새 기능 코드나 AI 추출 로직을 추가하지 않았다. frontend 소스와 Claude HTML 원본도 수정하지 않았다.
