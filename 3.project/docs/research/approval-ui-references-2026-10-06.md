# 결재·결재 요청·묶음 요청: 공식 제품 화면 조사와 설계 방향

2026-10-06 조사. 대상은 계약 증빙 검수 앱의 결재 화면, 사내 결재 요청, 거래처 묶음 요청이다. 현재 담당자·대표의 단순 흐름에서 결재자 3~5명으로 늘어나는 경우까지 고려한다. 사용자의 요청은 화면과 업무 흐름의 디자인 조사이며, frontend 구현은 Claude 담당으로 유지한다.

추천은 **넓은 흰 결재서 본문 + 별도 결재 영역**, 그리고 **받는 사람·요청 항목·미리보기·기록을 구분한 요청 창**이다. 기존 ‘지금 할 일’ 상자 안에 요약·이력·입력을 계속 쌓는 구조를 바꾸고, 제목·금액·변경 전후·검토자를 빠르게 읽을 수 있게 한다. 아래 제품의 관찰과 우리 앱에 대한 제안은 구분한다.

## 현재 화면과의 차이

[앞선 실제 화면 점검](../operations/approval_screen_review_20261006.md)의 main 앱 코드 `f27e8df`, 가상 8053 대표 화면, 1280×720 기준이다.

- 계약명이 상단에 있지만 금액은 작은 보조 문구다. 계약 요약 문장에 같은 정보가 다시 나온다.
- 큰 보라색 테두리 상자 안에 흰 요약 카드와 이력이 들어가 정보 계층이 여러 번 겹친다.
- 최근 처리 6건이 펼쳐져 승인/반려 버튼은 y≈1060px까지 내려간다.
- 우측 영역은 서류 종류 2줄에 주로 쓰여, 결재자·의견·결정 영역을 첫 화면에 두는 공간으로 활용하지 못한다.
- 담당 검토 사건의 제목/사람/시각은 보이지만 실제 의견은 표시되지 않는다.

이 관찰은 결재 기능이 실패한다는 뜻이 아니다. 대표가 읽고 판단하는 화면의 위계·공간 배치를 바꿀 이유다.

## Claude용 화면 설계 브리프

### 1. 페이지 틀

결재 단계에서는 ‘지금 할 일’의 큰 색 테두리와 중첩 카드를 줄인다. 계약 화면의 결재 영역을 하나의 흰 문서로 다루고, 데스크톱에서는 본문 약 2/3·결정 영역 약 1/3을 출발점으로 잡는다. 기존 내비게이션은 유지하되 단계 표시가 문서 제목·금액보다 더 강하지 않게 한다.

오른쪽은 **이번 결재** 영역이다. 현재 결재자/역할, 다음 단계, 남은 확인의 범위, 필요한 체크·메모·승인/반려가 한곳에 있다. 스크롤 중에도 찾기 쉽게 하되, 좁거나 낮은 화면에서는 겹치지 않는 세로 배치로 전환한다. 긴 입력창을 가진 패널을 무조건 고정해 포커스나 경고를 가리지 않는다.

### 2. 첫 화면의 정보 순서

1. **계약 제목과 금액:** 거래처·금액 기준·지급 방식은 짧은 정렬 항목. 가림 ON이면 현재 가림 규칙을 그대로 적용한다.
2. **이번 검토에서 달라진 것:** 문제 → 처리 → 현재 결과. 예를 들어 ‘견적 합계 3,520,000원 → 3,410,000원 / 고친 본 2번째 / 계약 기준금액과 일치’. 이 값은 시안용 가상 예시이며 실제 화면은 기록에서 채운다.
3. **담당자 검토:** 현재 자료를 검토한 사람·시각·의견. 기록이 없는 1단계 회사는 확인한 것처럼 표시하지 않는다.
4. **현재 증빙:** 현재 본을 먼저 보여 주고 원문/이전본 비교로 연결한다. 전체 처리 기록은 펼쳐 보기 또는 별도 탭이다.

### 3. 시각 규칙

- 배경은 옅은 회색, 본문은 흰색. 기존 보라색은 주 행동과 현재 상태에 제한적으로 사용한다.
- 제목·금액·작은 상태 배지가 먼저 읽히도록 글자 크기와 굵기를 나눈다. 시안 시작값은 제목 22~24px, 금액 28~32px, 본문 14~16px이며 렌더링 후 조정한다.
- 사실 정보는 긴 설명 문장 대신 라벨/값이 정렬된 행으로 표현한다. 본문 구분은 얇은 선과 여백을 우선한다.
- 승인 버튼은 주 행동, 반려는 별도 중립 버튼으로 둔다. 두 버튼을 전부 강한 색으로 만들지 않는다. 사유·확인 조건과 실제 저장 결과는 버튼 가까이에서 읽을 수 있어야 한다.
- 빨강/주황은 실패·남은 확인·지급 후 재결재 같은 실제 예외에 사용한다. ‘자동 검사 일치’를 계약 전체의 무조건 안전 판정으로 표현하지 않는다.

### 4. 기존 업무 의미와 연결 조건

기존 1/2단계 권한·차례·메모/체크 조건·revision/fingerprint 충돌 처리·자료 변경 후 재결재·이미 지급한 계약 경고를 유지한다. 확인 체크는 기본 선택하지 않는다. 이름만 바꿔 ‘반려’를 단순 메모로 축소하지 않는다.

대표에게 표시할 담당자 의견은 기존 approvals history의 현재 자료 기준 기록을 사용한다. `note`는 현재 원문 응답이므로 가림 ON에서 그대로 렌더링하면 안 된다. 표시용 가림 연결은 Codex와 맞춘다. 전체 이력의 일부만 조회해 ‘모든 변경 확인 완료’라고 쓰지 않는다.

실제 재발행/확인 기록이 없으면 문제나 처리 문장을 만들지 않는다. ‘지난 결재 이후 변경’은 실제 이전 결재 기준이 있을 때만 사용한다. 현재값 일치와 사람 원문 확인의 완료 여부는 별개다.

### 5. 시안 확인 조건

대표 결재 화면 한 장을 먼저 만든 뒤 같은 틀의 최초 결재·재결재·남은 확인·다른 역할 차례·이미 지급한 계약 상태를 확인한다. 별도 새 기능이 아니라 기존 상태별 화면 검증이다.

1280×720에서 계약명·금액·핵심 변경과 결재 행동의 위치가 처음부터 파악돼야 한다. 전체 이력이 많아져도 결정 영역이 끝없이 밀리지 않아야 한다. Tab 순서, 메모 입력, 경고 표시, 가림 ON/OFF, 긴 계약명과 문구도 확인한다.

### 6. 결재자 3~5명까지 고려한 구조

**현재 구현은 임의의 3~5명 결재를 지원하지 않는다.** [company_policy_service.py](../../backend/app/services/company_policy_service.py)의 approval_steps는 최대 2개, 역할은 operator/representative로 제한된다. 완료 계산은 최초 담당 검토 1건과 최종 대표 확인 구조다. [workflow.py](../../backend/app/api/workflow.py)의 SignoffRequest.step도 1~2이며 중간 결재는 first_signoff 하나를 기록한다. 제한 숫자만 늘리는 수정으로는 충분하지 않다.

추천 모델은 다음과 같다. 이는 조사 후 설계 제안이며 새 API 계약이 아니다.

- **결재 대상:** 계약과 현재 자료 기준, 요청자, 요청 시점, 결재 회차.
- **결재 단계:** 순서·단계 이름·실제 결재자 또는 지정 그룹·완료 규칙.
- **사람별 기록:** 대기/현재 차례/승인/반려/자료 변경으로 이전 확인 무효, 의견·시각·검토한 자료 기준.
- **권한:** 사내 직무 이름, 자료 수정 권한, 이번 결재 권한을 서로 구분한다. 개인 맡기기만으로 결재자가 되지 않는다.

화면은 2명의 원을 크게 놓고 복제하기보다 **접을 수 있는 결재 순서 목록**을 사용한다. 5명의 이름/직무/상태/의견을 줄 단위로 읽을 수 있고, 본문에는 ‘2/5단계 완료 · 지금 김○○ 검토 차례’처럼 짧게 요약한다. 이 문구는 순차 결재의 단계 수 기준이며 병렬 전원 동의를 ‘2/5단계’로 잘못 집계하지 않는다.

같은 단계의 여러 명이 전원 승인해야 하는지 한 명이면 되는지는 별도 정책이다. 예시 ‘담당 검토 → 팀장 → 재무 검토 → 부서장 → 대표’는 가상 시안이며 실제 회사에 이 직무가 있다는 가정은 아니다. 처음 구현할 확장 범위는 **지정된 사람이 순서대로 결재하는 N단계**를 권장하고, 병렬/대결/조건 분기는 별도 요구 확인 후 진행한다.

반려와 재결재는 화면 문구만으로 결정하지 않는다. 누가 반려하면 어느 단계로 돌아가는지, 자료가 바뀌면 어떤 확인이 무효인지, 결재 중 순서 변경은 어떤 회차에 적용되는지를 서버가 일관되게 정해야 한다. 요청 시점의 결재 경로와 자료 기준을 남겨 과거 이력이 현재 회사 설정으로 바뀌어 보이지 않게 한다.

난이도 판단: 가변 결재 목록을 보여 주는 UI는 중간, 현재 2단계 모델을 N단계의 사람별 기록·권한·재결재로 바꾸는 서버는 중상이다. 병렬 승인/대결/조건부 경로는 별도 범위로 난도가 더 높다. 일정 추정이나 지원 완료를 뜻하지 않는다.

### 7. 사내 결재 요청 창

현재 [ContractStageView.tsx](../../frontend/src/components/review/ContractStageView.tsx)의 사내 요청 부분은 요약 문장과 ‘대표님께 보낼 문장 복사’다. 수신자/결재 순서/이번 자료를 선택해 요청을 제출하는 전용 창이라고 표현하지 않는다. 자동으로 결재 차례가 계산되는 현행 흐름과, 명시적인 결재 요청 기능을 새로 만드는 일은 구분한다.

시안의 순서는 **결재 대상 → 결재 순서 → 검토 요점 → 최종 미리보기**다.

- 계약명·금액·현재 자료와 결재 회차는 자동으로 표시한다. 사용자가 제목/서류를 처음부터 다시 조합하지 않게 한다.
- 결재자가 1·3·5명일 때 같은 목록을 사용한다. 지정/순서 변경 권한이 없으면 읽기 전용으로 보여 준다.
- 전달 내용은 핵심 변경·담당자 의견·남은 확인의 정확한 범위다. 전체 처리 로그를 요청 본문에 붙이지 않는다.
- 마지막 행동 옆에 첫 수신자와 이후 순서를 보여 준다. 아직 실제 제출 API가 없는 시안에는 ‘서버 연결 예정’이라고 표시하고 클릭 시 요청된 것처럼 꾸미지 않는다.
- 명시적인 요청 제출을 도입하면 요청 전/결재 중/반려/재요청 상태와 변경된 자료 기준을 서버에 기록해야 한다. 복사 버튼을 요청 제출로 바꾸어 재사용하지 않는다.

### 8. 거래처 묶음 요청 창

현재 [BundleRequest.tsx](../../frontend/src/components/review/BundleRequest.tsx)의 창은 max-w-xl 안에 서류 이름의 연결 문자열, 짧게/자세히 문구, 복사 버튼, 연락 방법/기한/메모/기록 버튼을 세로로 둔다. 정정 대상 선택은 창 밖 목록에서 한다. 이 평가는 현재 코드를 읽은 구조 관찰이며 이번 조사에서 새 브라우저 재현을 한 것은 아니다.

시안은 다음 구조를 사용한다.

1. **대상:** 거래처·계약명·요청 항목 수. ‘새 요청 준비’라는 상태를 분명히 한다.
2. **요청할 것:** 서류명 / 요청 종류(미제출·내용 정정) / 이유를 정렬한 행. 3개 항목을 한 문장으로 묶어 숨기지 않는다. 사내 확인과 앱 판독 문제는 거래처 목록에서 계속 제외한다.
3. **문구 미리보기:** 선택한 항목으로 한 문구를 만들고 필요할 때 수정한다. 연락 형식 전환으로 수정한 글이 바뀌는 경우 내용을 잃지 않도록 전환/복원 방식을 정한다. 수정한 발송 문구가 현재 기록 메모와 동일하게 저장된다고 주장하지 않는다.
4. **실제 요청 후 기록:** 연락 방법·회신 기한·메모는 한 번만. ‘문구 복사’와 ‘요청한 것으로 기록’은 서로 다른 행동으로 유지한다. 아직 보내지 않았다면 요청 대기를 만들지 않는다.

항목 2~6개라면 단일 창에 정리할 수 있다. 긴 사유/항목이 많으면 넓은 패널이나 전용 화면을 검토한다. 모든 요청에 단계별 ‘다음’ 클릭을 강제하는 5단계 빌더는 제안하지 않는다. 모달 크기는 시안에서 결정하며 1280×720의 제목/닫기/행동 영역, 긴 문구, 좁은 창을 확인한다.

요청 뒤에는 **요청 1건의 요약 + 항목별 상태**를 함께 보여 준다. 예: ‘3건 중 2건 받음 · 1건 기다림’. 받은 사실과 내용 재검수 완료는 구분하고, 부분 수령·취소·재요청 경로를 유지한다. 자료 기준이 바뀌면 기존 원문 확인 동의를 재사용하지 않고 최신 선택을 받는다.

### 9. 공통 디자인과 우선순위

결재 요청과 거래처 요청은 제목/대상/본문/미리보기/하단 행동이라는 공통 틀을 사용할 수 있다. 안에 들어가는 업무는 다르다: 사내 요청은 결재 경로·검토 대상, 거래처 요청은 문서·사유·회신 기한이다. 서버 의미까지 한 가지 ‘요청 상태’로 합치지 않는다.

| 우선 | 문제·목표 | 근거·확신 | 진행할 보강 |
| --- | --- | --- | --- |
| 1 | 대표가 근거를 읽고 결정할 위치를 바로 찾기 | 실제 1280×720 화면 점검. 높음 | 결재서/결정 영역 분리, 핵심 변경, 담당 검토 의견 |
| 1 | 요청 대상을 해석하고 중복 입력하지 않기 | 현재 요청 코드와 공식 폼 구조 대조. 중간 | 대상·항목·문구·기록 영역의 공통 시안 |
| 2 | 3~5명의 현재 차례·의견·완료 기준 일관성 | 현재 최대 2단계 제약과 공식 다중 결재 정책. 높음 | N단계 순차 결재 모델/API 설계, 1·3·5명 화면 상태 |
| 후속 | 병렬/대결/조건부 결재를 어디까지 지원할지 | 참고 제품에는 존재, 실제 회사 요구는 아직 불명 | 사용자 업무 정책 확인 후 범위 결정 |

사용자 불편 빈도·처리 시간 효과는 아직 측정하지 않았다. 시안에서는 정상 한 장뿐 아니라 부분 회신·긴 사유·반려·재결재·다른 사람 차례를 함께 검토한다. 이를 근거로 기능과 UI를 정리한 뒤 구현한다.

이 브리프는 연구·시안 요청까지다. frontend를 수정하거나 측정 빌드에 자동 반영하지 않았다. 화면 확정 후 구현·연결·관련 검증·통합 순서로 진행한다. Codex는 결재 모델/권한/API 의미, Claude는 공통 화면 틀과 각 업무 화면 시안을 맡는 기존 역할을 유지한다. 다른 채팅에 전달 메시지를 보내지 않았다.
