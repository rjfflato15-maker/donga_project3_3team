# 대표 화면 + 업무 흐름 비교 HTML 구성안

2026-10-06. 사용자 요청: Claude `docs/ux/compare/ui_compare.html`처럼 비교하되 대표 화면과 실제 업무 흐름을 모두 보기 좋게 묶는다. 현재 HTML은 6쌍의 대표 화면 비교이며 전체 사용 흐름 비교는 아니다. 이 문서는 확장 제작 규격이다. 기존 비교 HTML이나 실제 앱을 이번에 수정한 것은 아니다.

## 한 파일, 두 가지 읽는 방식

상단에 `대표 화면 / 업무 흐름 / 예외·모바일 / 의견 정리`를 둔다. 대표 화면은 빠르게 디자인을 고르는 구역, 업무 흐름은 현재 단계에서 다음 행동을 이해할 수 있는지 보는 구역이다. 같은 화면이 양쪽에 등장할 수 있지만 질문을 다르게 한다.

- 좌측: 현재 구조. 재현 HTML 캡처라면 ‘현재 구조 · 재현 시안’이라고 표시한다.
- 우측: 비교할 새 안. Claude ERP안과 Codex 사이드바안은 선택해서 한 안씩 보여 준다. 세 화면을 좁은 3열에 한꺼번에 놓지 않는다.
- 새 안 선택과 단계 이동은 비교 도구의 기능이다. 앱 실제 메뉴처럼 그리지 않는다.
- 이미지 확대와 독립 클릭 시안 링크를 제공한다. 화면 캡처의 버튼이 실제 저장/발송을 한다고 느끼게 만들지 않는다.
- 독립 HTML은 이미지·스타일을 포함한다. 의견은 브라우저에서 입력/복사하며 서버로 전송하지 않는다. 스크립트가 막히면 기본 비교와 모든 단계의 링크/내용을 읽을 수 있게 한다.

## 1. 대표 화면: 기존 6쌍 유지

| 화면 | 볼 것 | 질문 |
| --- | --- | --- |
| 업무함 | 메뉴·목록·차례·다음 행동 | 지금 처리할 계약을 찾을 수 있는가? |
| 계약 상세 | 계약 요점·서류·문제·행동 | 무엇을 먼저 해야 하는지 알 수 있는가? |
| 원문 대조 | 원문·저장값·근거·출처·사람 확인 | 앱이 잘못 읽은 것과 서류 내용이 다른 것을 구분할 수 있는가? |
| 요청 작성 | 요청 항목·문구·기한·복사/기록 | 무엇을 보내 달라는 것인지, 언제 기록하는지 알 수 있는가? |
| 부분 회신 | 받은 항목·남은 대기·검사 | 받음과 검사 통과를 구분할 수 있는가? |
| 대표 결재 | 변경·근거·남은 확인·결정 | 무엇을 보고 승인/반려해야 하는지 알 수 있는가? |

상태가 다른 이미지를 외관 참고로 쓰는 경우 ‘예시 자료/상태 다름’을 표시한다. 업무 수행 비교에는 반드시 같은 자료를 사용한다. 사이드바는 사용자 선택대로 접고 펼치는 왼쪽 메뉴를 적용한 새 안을 기준으로 한다. 초기 상단 ERP안을 보존하면 ‘초기 탐색안’으로 구분한다.

## 2. 업무 흐름: 같은 계약으로 전후를 따라가기

각 단계에 `사용자 역할 / 지금 상황 / 할 행동 / 행동 후 결과` 네 정보를 짧게 표시한다. 그 아래 현재/새 안을 나란히 둔다. `이전 / 다음`은 양쪽을 같은 업무 단계로 이동시킨다. 서로 다른 클릭 수를 강제로 같게 맞추지 않으며, 합쳐진 단계는 한쪽의 이동 경로를 표시한다.

### 정상 처리: 짧은 흐름

업무함 → 계약 등록·서류 선택 → 읽은 계약 기준 확인 → 원문·필수 서류 검토 → 담당자 확인/대표 전달 → 대표 결정 → 지급 기록·완료.

회사의 현재 결재 정책을 양쪽에 동일하게 적용한다. 담당자와 대표가 두 명 등장한다고 모두 담당자 승인→대표 승인 2단계인 것은 아니다. 현행 전달 문장 복사를 명시적 상신 API로 바꾸지 않는다.

### 보완 처리: 주 비교 시나리오

같은 가상 계약 ‘새봄기획 / 업무지원 시스템 구축 / 부가세 포함 3,410,000원’을 사용한다. 최초 필수 서류는 6종 중 4종, 빠진 외부 서류는 통장사본·세금계산서다. 최초 견적서 원문과 저장값은 모두 3,520,000원이다. 앱은 정확히 읽었고 서류 금액이 계약과 다른 상황이다.

| 단계 | 역할·상황 | 행동·결과 | 기존 자료 활용 |
| --- | --- | --- | --- |
| 1 | 담당자 · 업무함 | 계약 등록 시작 | B1 / C1 |
| 2 | 담당자 · 등록 자료 | 계약 기준값 확인, 등록 | C2 |
| 3 | 담당자 · 받은 4/6종 | 빠진 2종과 견적서 금액 차이 확인 | S1 |
| 4 | 담당자 · 견적서 원문 | 원문과 저장값이 같음을 확인. 값을 계약에 맞춰 수정하지 않음 | E1에 같은 자료로 맞춘 상태 |
| 5 | 담당자 · 보완 필요 | 빠진 2종+견적서 정정을 한 요청으로 준비 | S2 |
| 6 | 담당자 · 외부에서 요청함 | 연락 방법·기한으로 한 번 기록 | S2 저장 후 상태 |
| 7 | 담당자 · 일부 회신 | 통장사본·세금계산서 수령, 견적서는 계속 대기 | S3 |
| 8 | 담당자 · 정정 견적서 도착 | 같은 논리 문서의 고친 본으로 업로드 | S4 |
| 9 | 담당자 · 현재 견적서 2번째 본 | 3,520,000→3,410,000 비교, 원문 재검토, 남은 회신 기록 | S5 |
| 10 | 담당자 · 문제 해결 | 현행 정책의 다음 결재 차례/대표 전달 확인 | S6 |
| 11 | 대표 · 자기 차례 | 변경·근거·미조회 사항 검토, 의견과 확인 후 결정 | S7 |
| 12 | 담당자 · 최종 결재 완료 | 계약 전체 지급 기록, 완료 상태 확인 | D7 / D9 |

시안 단계 넘기기는 준비된 화면을 따라가는 기능이다. 실제 파일 처리·AI 실행·승인 저장이 이루어진 것과 구분한다. ‘몇 초 빠르다’거나 실제 업무 시간이 줄었다는 결론은 정적 이미지에서 내지 않는다.

## 3. 예외·모바일: 관련 단계에 연결

- 대표 반려 → 이유 확인 → 자료 보완 → 재검토·재결재.
- 원문이 흐리거나 근거 없음 → 확인 필요 유지. 판독 실패를 거래처의 서류 내용 오류로 처리하지 않는다.
- 저장 충돌 → 저장 실패 이유 → 최신 상태 재조회 → 다시 확인.
- 이미 지급한 뒤 자료 변경 → 재결재·같은 지급 재확인. 새 지급으로 중복 기록하지 않는다.
- 모바일은 업무함·대표 결재·원문 확인 3개부터 보여 준다. 사이드바 메뉴/현재 위치와 원문-값 전환을 비교한다. 기존 모바일 자료가 없으면 없는 것으로 표시한다.
- 3~5명 결재선은 별도 ‘후속 기능 제안’에 둔다. 현재와 같은 기능이라고 표기하지 않는다.

## 현재 자료의 준비 범위

- Claude 현재 구조 재현: flow_prototype의 S1~S7과 등록/원문/지급 등 캡처가 있다. 날짜·용어·현재 앱 기준과 같은 데이터인지 제작 때 확인한다.
- Claude ERP형: 대표 화면·값 수정·충돌·재발행·부분 회신·결재·반려·지급 재확인 예시는 있다. 정상 등록~완료의 모든 단계가 준비된 것은 아니다. W6S의 상신 의미 등 앞선 API 검토 정정을 반영한다.
- Codex형: 업무함/계약/원문/대표 결재와 묶음 요청/부분 회신 클릭이 있다. 대표 결재 계약과 요청 계약이 다르고 등록은 간단한 입력, 파일 선택은 저장하지 않는 시안이다. 위 보완 시나리오와 동일한 상태를 추가로 준비해야 한다. 기존 스크린샷만 순서대로 붙여 전체 흐름이라고 하지 않는다.

## 의견 정리

대표 화면에는 ‘읽기 쉬운 쪽 / 이해하기 어려운 곳’, 업무 흐름에는 ‘다음 행동이 막힌 단계 / 처리 결과를 오해한 단계’를 묻는다. 마지막에 공통 톤·목록 밀도·결재 입력 위치·용어를 정리한다. 화면 선호와 새 기능 추가 결정을 한 질문으로 섞지 않는다.

제작 순서: 비교 대상의 현재/제안 범위 명시 → 같은 사례의 단계별 상태표 → 빠진 새 시안 제작 → 동일 크기/상태 캡처 → 비교 HTML 통합 → 실제 사용자에게 화면/흐름 질문. 실제 앱 반영은 별도 작업이다.
