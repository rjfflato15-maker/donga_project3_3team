# Claude에게 보낼 Codex 사이드바 구현 명세 요청

사용자 결정: 디자인은 Codex 새안으로 확정. Claude는 명세서 작성, Codex는 실제 frontend 구현·검증. Claude의 사용량은 1회 명세 작성과 가능하면 최종 시각 검토에 남긴다.

아래 내용을 한 번의 요청으로 전달한다. 이 파일 작성은 Claude에게 메시지를 보냈거나 명세서가 완성됐다는 뜻이 아니다.

## 복사할 요청문

```text
팀원 모두 Codex 사이드바 새안에 동의했어. 네 남은 사용량을 고려해 실제 frontend 구현은 Codex가 맡고, 너는 승인된 시안을 구현 명세서로 정리해 줘.

main 최신 문서를 먼저 가져온 뒤 docs/ux/codex_sidebar_ui_spec.md 한 파일로 작성해 줘. 앱 코드와 기존 시안은 수정하지 말고, 새 디자인·리서치·캡처를 추가하지 않아도 돼. 파일 작성 후 로컬 커밋과 경로를 알려 줘. push·PR은 하지 마.

[디자인 기준]
- docs/ux/codex_sidebar_example/ui_compare.html의 오른쪽 Codex 새안
- docs/ux/codex_sidebar_example/codex-workflow.html: 같은 계약의 업무 흐름
- 세부 구현 참고: 같은 폴더 src/App.jsx, src/StoryPreview.jsx, src/prototype.css, src/story.css
- docs/ux/codex_sidebar_example/comparison-README.md: 시안의 범위와 가상 데이터 제한
- Claude ERP 시안은 이번 구현안에 섞지 마. 승인된 왼쪽 사이드바·접기/펼치기·색상·배치·정보 밀도를 유지해 줘.

[실제 동작 기준]
- docs/ux/codex_sidebar_implementation_handoff_20261006.md
- docs/api/frontend_handoff.md, work_system.md, bundled_requests.md, payment_record.md
- 현재 frontend의 API·권한·상태 계산·입력 검증을 재사용. 새로운 API나 업무 기능은 설계하지 마.
- 시안의 가상 계약·고정 날짜·준비된 단계 이동·로컬 승인/지급 성공 처리는 실제 동작으로 옮기지 않아.

[명세서에 필요한 7가지]
1. 화면 지도: 주요 6종(업무함, 계약 상세, 원문 대조, 묶음 요청, 부분 회신, 대표 결재)과 등록·재발행·지급·완료·검색·맡기기·설정의 연결. 각 화면에서 기존 컴포넌트와 API/데이터 출처를 적어 줘.
2. 디자인 토큰: 실제 CSS에서 색상, 글꼴, 글자 크기/굵기, 간격, 경계선, 모서리, 버튼 높이, 사이드바/본문 크기, 표·탭·모달 규칙을 추출해 줘. 추측한 값은 별도로 표시해 줘.
3. 컴포넌트 규격: 공통 셸, 사이드바, 계약 헤더, 탭, 표, 상태 배지, 결재선, 요청/회신 패널, 모달의 배치·선택·hover·focus·disabled 상태. 반복 요소를 한 규격으로 묶어 줘.
4. 동작 표: 주요 버튼·입력의 행동, 호출할 기존 기능, 활성 조건, 성공 후 이동/유지/초기화, 실패 후 안내·재시도. 상태는 서버 stage/work_state/next_actions를 기준으로 해 줘.
5. 예외 상태: 로딩, 빈 목록, 판독 불가, 부분 회신·취소, 반려, 자료 변경 후 재결재, 409 충돌, 세션 만료, 업로드 실패, 이미 지급한 계약의 재확인. 실제 앱에 있는 조건과 문구를 유지해 줘.
6. 마스킹·반응형·키보드: 아래 마스킹 조건과 1440×900/1280×720/390×844에서 배치, 모바일 메뉴·원문/읽은 값 전환, Tab/Shift+Tab/Esc/포커스 복귀를 명세해 줘.
7. 구현 순서와 확인 목록: 공통 셸·업무함 → 상세·탭 → 원문 대조 → 묶음 요청·회신 → 결재 → 지급·다운로드 → 나머지 화면. 단계별로 시안과 비교할 항목과 실제 흐름 확인 기준을 적어 줘.

[확정된 마스킹 조건]
- 사업자번호만 가리는 것으로 줄이지 않아.
- 일반 조회의 거래처명·읽은 값의 상호/사업자번호/계좌번호와, 검사 문장 속 사업자번호/주민번호는 현재 로직대로 가려.
- 원문은 자동 감지한 번호·계좌·연락처·주소·이메일·상호·대표자명 등을 가리며 누락 가능성 안내를 유지해.
- 값 수정칸에는 실제 값, 거래처 요청 문구에는 실제 거래처명이 들어가. 예외 안내를 유지해.
- 처리 이력 화면의 사내 처리자 이름은 유지해.
- ZIP은 ON이면 서류·JSON 가림, OFF이면 원본. '가린 원본 받기'는 OFF 상태에서도 가린 파일을 받아.
- 토글은 저장 원본·DB를 삭제하거나 암호화하는 기능이 아니야.

[구현 범위]
- SMALL_BUSINESS 대표 1단계, MID_SIZED 담당 검토→대표 최대 2단계. 3~5명 결재선은 아직 없어.
- 대표 전달은 문장 복사이며 명시적 상신 API·자동 발송은 없어.
- 고친 본을 특정 요청 항목에 영구 연결했다는 표현은 쓰지 마.
- 지급은 사실 기록이며 실제 송금이 아니야.
- 국세청 disabled, 실제 LLM 상태, revision/fingerprint, 중복 방지, 늦은 응답 무시, 역할 권한은 유지해.
- 현재 구현에서 판단하기 어려운 것은 '확인 필요'에 짧게 모으고, 명세서 전체 작성은 마쳐 줘.

결과는 명세서 경로와 커밋, 확인 필요 항목만 짧게 알려 줘. 이 명세서를 받은 Codex가 실제 화면에 반영할 거야.
```

## 요청 후 받을 것

- `docs/ux/codex_sidebar_ui_spec.md`
- 로컬 커밋 SHA 또는 실제 파일 경로
- 기존 API로 대응할 수 없거나 시안과 충돌하는 사항

Codex는 파일을 읽고 구현 기준과 대조한 뒤 시작한다. Claude의 답변을 받기 전에는 명세가 완성됐다고 간주하지 않는다.
