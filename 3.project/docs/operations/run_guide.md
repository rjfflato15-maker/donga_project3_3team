# C업체 시범 앱 실행과 운영 안내

평소에는 프로젝트 폴더의 `C-Pilot.exe`를 더블클릭한다. 서버 준비를 확인한 뒤 브라우저가 열린다. 다시 실행하면 실행 중인 같은 서버에 연결한다. 실행 창이나 브라우저를 닫아도 서버는 계속 실행되며, 종료할 때는 실행 창에서 M을 입력하고 관리 메뉴 9번을 선택한다. 자료 분석이 끝난 뒤 종료한다.

## 처음 준비하기

Git 소스에는 생성된 EXE를 포함하지 않는다. 처음에는 `start_pilot.bat`을 실행하면 `tools/build_launcher.ps1`이 Windows .NET Framework 컴파일러로 EXE를 만들고 실행한다. 이후에는 EXE 하나를 사용한다. 실행 파일을 다시 만들려면 `tools/build_launcher.ps1`을 실행한다. 소스가 변경되면 `start_pilot.bat`도 다시 빌드한다.

새 PC에는 Python 3.12와 Node.js·npm을 설치한다. Python은 Windows `py -3.12` 명령으로 찾을 수 있어야 하고 Node.js와 npm은 PATH에서 찾을 수 있어야 한다. 관리 메뉴 3번에서 프로젝트 전용 `backend/.venv` 생성, 필요한 Python 패키지 설치, `npm ci`, 화면 빌드를 진행한다. 설치나 빌드에 실패하면 완료로 표시하지 않는다. 기존 실행 환경이 준비되어 있으면 매번 설치하지 않는다.

환경 준비는 패키지 다운로드가 필요하다. 인터넷이 없는 망에는 IT 담당자가 검증한 설치 프로그램·Python 패키지·Node 패키지·화면 빌드를 반입해 준비한다. 이번 작업에 오프라인 설치 패키지 생성·검증 기능까지 구현하지는 않았다. Ollama와 모델도 별도 설치 항목이며 통합 실행기는 LLM을 활성화하지 않는다.

관리 메뉴 4번의 **빈 업무함 만들기**는 새 회사용이다. **기존 자료 가져오기**는 기존 DB 설정의 자료를 읽어 이주하는 별도 선택이며 자동 실행하지 않는다. 이미 `pilot.db`가 있으면 덮어쓰지 않는다. 초기 계정은 지정 자료 폴더의 `initial-accounts.txt`에서 확인하고 첫 로그인 후 비밀번호를 바꾼다. 이 파일은 공유하거나 Git에 넣지 않는다.

EXE는 Python 프로그램을 호출하는 작은 실행 입구다. 앱 폴더와 실행 환경이 함께 필요하다. EXE만 따로 옮기거나 기존 `.venv` 폴더만 다른 PC에 복사하는 방식은 지원하지 않는다. Python과 모델까지 포함한 단독 설치형 배포는 향후 범위다.

## 설정과 관리 메뉴

| 번호 | 기능 | 사용 시점 |
| --- | --- | --- |
| 1 | 앱 실행 | 서버 준비 확인 후 브라우저 열기 |
| 2 | 상태 점검 | Python·화면 빌드·업무함·서버 상태와 로그 위치 확인 |
| 3 | 최초 환경 준비 | 새 PC의 패키지 설치와 화면 빌드 |
| 4 | 업무함 준비 | 새 DB 생성 또는 기존 자료 이주 |
| 5 | 실행 설정 | 서버 종료 후 포트·자료 폴더·백업 폴더·사내망 사용 변경 |
| 6 | 지금 백업 | 지정 백업 폴더에 새 ZIP 생성 |
| 7 | 새 폴더에 복원 | 서버 종료 후 백업을 새 자료 폴더에 복원하고 설정 전환 |
| 8 | 자동 실행·백업 | 사용자가 선택할 때 Windows 예약 작업 등록 |
| 9 | 서버 종료 | 이 실행기가 시작한 서버만 종료 |
| 0 | 관리 창 닫기 | 서버는 계속 실행 |

실행 설정은 `storage/launcher/settings.json`, 서버 실행 기록과 로그도 같은 폴더에 저장한다. 설정에는 비밀번호를 저장하지 않는다. 회사명·직원 계정·필수서류는 로그인 후 기존 앱의 **업무 설정 · 계정**에서 관리한다. 화면과 디자인은 이번 작업에서 변경하지 않았다.

기본값은 포트 8000, 자료 `storage/pilot`, 백업 `storage/backups`, 현재 PC에서만 접속이다. 변경한 설정은 다음 실행과 예약 작업에도 적용한다. 업무 자료 안에 백업을 중복 보관하지 않도록 백업 폴더는 자료 폴더 밖으로 지정한다. 설정·복원·환경 설치는 실행 중인 서버를 종료한 뒤 진행한다.

포트가 다른 프로그램에 사용 중이면 그 프로그램에 접속하거나 종료하지 않고 안내한다. 실행 작업은 파일 잠금으로 중복을 막는다. 서버 재사용은 고유 실행 식별자와 실제 프로세스를 확인하고, 종료는 프로세스 ID·생성 시각·실행 경로를 비교한 같은 Windows 핸들에만 적용한다. 서버 로그에는 웹 접근 로그를 기록하지 않으며 LLM도 비활성 상태다. 실행 기록은 운영 기록이며 복제 탐지나 라이선스 감시 기능이 아니다.

## 로그인과 퇴사 처리의 현재 상태

| 항목 | 구현된 동작 또는 남은 범위 |
| --- | --- |
| 로그인 | 등록된 이메일과 비밀번호로 로그인. 무작위 salt를 쓰는 PBKDF2 해시 저장, 초기 비밀번호 변경 요구 |
| Caps Lock | 비밀번호 입력 중 Caps Lock 경고. 입력 편의 기능이며 추가 인증은 아님 |
| 반복 실패 | IP·이메일별 5분 안에 8회 시도 시 제한. 단일 서버 메모리 기반이며 재시작 후 유지되는 계정 잠금은 아님 |
| 로그인 유지 | HttpOnly·SameSite 쿠키, 서버의 세션 해시와 만료 확인. 비밀번호 변경 시 기존 세션 모두 폐기 |
| 역할 | 담당자와 대표의 권한을 API에서도 확인 |
| 직원 퇴사 | 대표가 해당 계정을 비활성화하면 모든 기존 세션 폐기·새 로그인 차단. 계약과 감사 이력은 보존 |
| 2차 인증 | 현재 미구현. 판매 전 회사 요구에 따라 인증 앱의 일회용 번호(TOTP) 또는 사내 SSO 연계 검토 |

계정 비활성화로 이미 내려받은 파일까지 회수할 수는 없다. 퇴사 절차에는 사내 PC·공유폴더·백업 접근 권한 회수도 포함한다. 앱 계정 관리와 Windows 자료 폴더 접근 권한은 별도로 관리한다.

## 다른 PC에서 사용하기

같은 회사에서 사용할 때는 자료를 PC마다 복제하기보다 서버 PC 한 대를 유지하고 직원 PC는 브라우저로 접속하는 구조다. 실행 설정의 사내망 허용을 켜고 `http://서버의사내IP:포트/`로 접속한다. 서로 다른 직원은 개인 계정을 사용한다. 다른 브라우저와 PC의 로그인 세션은 각각 생성되며 계정 비활성화·비밀번호 변경은 해당 계정의 세션 전체에 적용한다.

통합 실행기는 기본적으로 로컬 HTTP이고, 사내망 옵션은 바인딩 주소를 바꾸는 기능이다. HTTPS·인증서·방화벽·VPN을 자동 구성하지 않는다. 실제 회사의 로그인·문서 통신을 보호하려면 IT 담당자가 HTTPS와 회사 대역 접근 제한을 준비한다. HTTPS 역방향 프록시 운영은 별도 설정으로 `APP_COOKIE_SECURE=true`와 접속 주소를 적용한다. 현재 간편 실행기는 HTTP용 쿠키 설정을 사용하므로 그 상태로 HTTPS 운영 완료라고 설명하지 않는다.

서버 PC를 교체할 때는 기존 서버를 종료하고 백업한 뒤 새 PC의 실행 환경을 준비한다. 백업을 새 자료 폴더에 복원하고 접속 주소를 변경한다. SQLite DB 파일을 여러 PC에서 네트워크 공유로 동시에 직접 여는 방식은 지원 경로가 아니다.

## 백업과 복원

관리 메뉴 6번은 실행 중에도 기존 백업 도구의 DB 스냅샷과 원문 자료를 ZIP으로 생성한다. 백업에는 초기 계정 비밀번호 안내 파일을 포함하지 않는다. ZIP 자체는 암호화하지 않으므로 회사가 정한 암호화 저장소와 접근 권한, 보관 기간을 적용한다.

7번 복원은 서버가 종료되어 있고 아직 존재하지 않는 새 폴더에서만 진행한다. 기존 복원 도구가 파일 경로와 해시를 확인한다. 복원에 성공한 다음 실행 설정의 자료 폴더를 바꾸며, 실패하면 현재 설정은 유지한다. 복원된 DB의 로그인 세션은 모두 만료되어 다시 로그인해야 한다. 이전 업무함은 자동 삭제하지 않는다.

8번 예약 작업은 사용자가 직접 등록할 때만 생성된다. 자동 실행은 **현재 Windows 사용자가 로그인한 뒤** 시작한다. 자동 백업 기본 시각은 18:00이다. 로그인 전 부팅 서비스, 서버 장애 후 상시 재시작 감시, PC가 꺼져 있을 때 백업, 자동 실패 알림까지 구현한 것은 아니다. 해제는 Windows 작업 스케줄러의 `C-Pilot-Contract-App`, `C-Pilot-Daily-Backup`에서 비활성화하거나 삭제한다.

## 유지보수와 판매 전에 정할 사항

현재는 실행 로직을 `backend/pilot_launcher.py`, 기존 업무함 관리 로직을 `backend/manage_pilot.py`, EXE 진입점을 `tools/launcher/Program.cs`로 나누어 관리한다. 앱 화면과 AI 코드에 실행 설정을 섞지 않는다. 버전 변경은 변경 기록과 테스트 결과를 남기고 로컬 커밋으로 보관한다. 가드 v3의 평가 고정 파일은 별도로 유지한다.

고객 업데이트 절차는 **버전 확인 → 백업 → 서버 종료 → 검증한 앱 파일 교체 → 실행 환경과 DB 변경 확인 → 시작·로그인·문서 조회 확인**으로 정한다. 자료·백업·고객 설정 폴더는 앱 파일 교체 대상에서 제외한다. DB 구조를 바꾼 버전은 전용 이주와 복구 검증을 준비해야 하며, 이전 코드만 되돌리면 DB도 복원된다고 가정하지 않는다. 이번 작업에 자동 업데이트·서명 검증·DB 버전 이주 체계를 구현하지는 않았다.

| 회사 환경 | 가능한 유지보수 경로 | 사전에 필요한 합의 |
| --- | --- | --- |
| 회사가 승인한 원격 접속 가능 | 회사 VPN 등으로 승인된 작업 시간에 지원 | 접속 계정·권한·작업 기록·고객 승인 |
| 외부 접속은 막고 파일 반입 가능 | 검증한 업데이트 묶음과 안내를 전달해 사내 담당자가 적용 | 반입 절차·검증·백업·복구 방법 |
| 외부 접속과 파일 반입이 모두 제한 | 현장 방문 또는 회사 내부 관리자가 승인된 절차로 작업 | 일정·작업 범위·방문 비용 |

판매 구조는 **고객이 사용할 권리**와 **업데이트·장애 대응·복원·호환성 유지 지원**을 구분해 정한다. 고객이 설치된 프로그램을 AI로 분석하고 기능을 추가하거나 직접 유지보수하는 일을 완전히 막을 수는 없다. 고객이 직접 수정한 부분은 원래 제품의 지원 범위와 분리하고, 지원을 재개하려면 수정 내역을 확인하는 조건을 정할 수 있다. 실제 계약 문구와 라이선스 의무는 별도로 검토해야 한다. 유지보수비의 근거는 공식 버전의 검증과 지원 범위이며 고객의 수정 권한을 기술적으로 잠그는 기능이 아니다.

고객 PC에 전달된 코드의 복제나 유사 기능 재개발을 완전히 차단하는 기술을 약속하지 않는다. [WIPO 안내](https://www.wipo.int/en/web/copyright/activities/software)는 프로그램의 표현과 기능·아이디어의 보호 범위를 구분한다. 난독화나 실행 파일 포장은 소스 복원과 수정의 비용을 높이는 수단일 뿐 완전한 차단 수단은 아니다. 현재 EXE는 Python 소스를 숨기지도 않는다.

향후 필요하면 회사별로 서명한 오프라인 라이선스와 고객이 승인한 진단 자료 내보내기를 검토한다. 라이선스 위변조 검사도 고객 PC 관리자에 의한 우회를 완전히 막지는 못한다. 복제를 감지했다며 몰래 외부에 연락하거나 업무 자료를 보내는 기능은 구현하지 않는다. 완전히 격리된 사내망에서는 외부 자동 연락 자체가 불가능하다.

[GitHub 공식 안내](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)에 따르면 공개 저장소의 코드는 누구나 볼 수 있다. 공개 저장소 안의 별도 브랜치도 비공개 판매용 소스 보관소가 되지 않는다. 판매용 소스를 보호하려면 공개할 제출·시연 자료와 비공개 팀 소스의 범위를 먼저 정한다. 이번 작업은 push·PR·저장소 공개 범위 변경을 하지 않는다.
