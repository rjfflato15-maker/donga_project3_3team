# 배포·소스 노출·판매 검토

판매 구조는 **고객이 사용할 권리**와 **업데이트·장애 대응·복원·호환성 유지 지원**을 구분해 정한다. 고객이 설치된 프로그램을 AI로 분석하고 기능을 추가하거나 직접 유지보수하는 일을 완전히 막을 수는 없다. 고객이 직접 수정한 부분은 원래 제품의 지원 범위와 분리하고, 지원을 재개하려면 수정 내역을 확인하는 조건을 정할 수 있다. 실제 계약 문구와 라이선스 의무는 별도로 검토해야 한다. 유지보수비의 근거는 공식 버전의 검증과 지원 범위이며 고객의 수정 권한을 기술적으로 잠그는 기능이 아니다.

고객 PC에 전달된 코드의 복제나 유사 기능 재개발을 완전히 차단하는 기술을 약속하지 않는다. [WIPO 안내](https://www.wipo.int/en/web/copyright/activities/software)는 프로그램의 표현과 기능·아이디어의 보호 범위를 구분한다. 난독화나 실행 파일 포장은 소스 복원과 수정의 비용을 높이는 수단일 뿐 완전한 차단 수단은 아니다. 현재 EXE는 Python 소스를 숨기지도 않는다.

향후 필요하면 회사별로 서명한 오프라인 라이선스와 고객이 승인한 진단 자료 내보내기를 검토한다. 라이선스 위변조 검사도 고객 PC 관리자에 의한 우회를 완전히 막지는 못한다. 복제를 감지했다며 몰래 외부에 연락하거나 업무 자료를 보내는 기능은 구현하지 않는다. 완전히 격리된 사내망에서는 외부 자동 연락 자체가 불가능하다.

[GitHub 공식 안내](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)에 따르면 공개 저장소의 코드는 누구나 볼 수 있다. 공개 저장소 안의 별도 브랜치도 비공개 판매용 소스 보관소가 되지 않는다. 판매용 소스를 보호하려면 공개할 제출·시연 자료와 비공개 팀 소스의 범위를 먼저 정한다. 이번 작업은 push·PR·저장소 공개 범위 변경을 하지 않는다.

폴더별 배포 대상은 [배포 경계](../development/distribution_boundary.md)를 참고한다.
