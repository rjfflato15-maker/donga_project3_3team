# 제품 기반 보강 + UX 수정

## 최신 54ef79e 병합·제품 확인 (2026-10-05)

`ffbc55a`·`54ef79e`를 병합하고 직접 frontend **52개·빌드 통과**. 새 가상 8053 업무함에서 R2 마지막 항목 충돌→결재 전환 안내 유지, 도착 안내/자동 체크 없음, 업로드 훅 순서·실패 파일 취소를 확인했다. 기존 R2는 완료다. [최신 점검](../research/bundled-request-ui-audit-2026-10-05.md)에 새 **R3 역할 건수/안내 불일치**, **R4 취소 파일의 다른 계약 이동**을 기록했다. 서버의 결재 권한은 올바르며 frontend 연결과 창 상태 초기화가 남는다. 실제 다른 계약 업로드는 실행하지 않았다.

Claude는 R4 파일 생명주기/스크롤, R3 공통 역할 판단을 보완한다. Codex는 해당 컴포넌트 경로를 다시 확인한다. 참가자 안내·배포 사본/해시는 묶음 요청과 선택 수령으로 동기화했고 원문 과제·정답·회신·ZIP 5개는 보존했다. 측정 SHA는 아직 미확정으로 관련 수정·최신 측정 서버·사용자 ZIP 저장 확인 후 별도 고정한다. 제품 기반 보강 범위와 실제 자료/보호 평가 분리 원칙은 유지한다.

## 이전 45e2bda 화면 병합·재확인

Claude의 `021f05d`·`d61d9c0`·`110500e`·`45e2bda`를 main에 병합했다. frontend **50개·빌드 통과**. 새 별도 가상 8052 업무함에서 금액 정정 대상, 자동 검사 범위, 현재/이전본, 처리 이력, 대표 요약, 서버 검색·대기 중 사내 확인을 직접 확인했다. 처리자 이름은 인증된 activity에서 보존하도록 서버를 수정했고, 사건 메모/ZIP 가림을 유지하는 관련 **34개 검사 통과**다.

R1의 세대 검사와 계약 전환 초기화는 반영됐지만, R2는 마지막 회신 종료 뒤 **결재 단계로 이동하면 409 안내가 사라지는 경계**가 남는다. 실제 두 탭으로 재현했고 [상세 점검](../research/bundled-request-ui-audit-2026-10-05.md)과 [Claude 인계](../api/frontend_handoff.md)에 수정·완료 조건을 적었다. ‘묶음 수정+R1·R2 검증 완료’를 전제로 구버전을 동결하지 않는다. 이 경계와 사용자 ZIP 확인을 닫은 최신 검증 SHA로 측정 버전을 별도 고정한다.

제품 작업 범위는 유지한다. 다음 frontend 묶음은 회신 대기 시 다음 행동, 역할 업무와 개인 맡기기의 구분, 실패 파일 취소/ADD·REISSUE 재확인이다. 과제 완료에 필요한 오류가 발견되면 측정 확정 전에 수정한다. 측정 빌드 확정 후에는 후속 개발 HEAD가 바뀌어도 참가자 빌드를 자동 갱신하지 않는다.

사용자의 최신 지시: 테스트를 위한 화면 문구 정리에 한정하지 않고 **상태·이력·재작업·업무 통제·검색 5가지 제품 기반 보강과 UX 오류 4건**을 함께 진행한다. `38f53f2`의 테스트 전 UI 한정 계획을 이 범위로 확대한다. 날짜를 기다리지 않고 선행 데이터/기능이 준비된 범위부터 구현한다.

## 기준과 역할

Codex는 서버 공통 상태·저장 기록·API·관련 회귀 검증·인계·병합을 맡는다. Claude는 frontend의 기존 UX 4건과 새 데이터 연결을 맡는다. 서로 같은 화면 파일을 동시에 수정하지 않는다. 화면 수정만 끝났다고 업무 기반 보강이 완료된 것으로 세지 않는다.

기존 재작업 코어를 새로 중복 구현하지 않는다. ‘담당자 확인 완료’는 실제 필드 확인/담당 결재가 있을 때만 쓴다. 기본 1단계 회사의 대표 결재 권한을 UI 수정 과정에서 임의로 2단계로 바꾸지 않는다.

## 오늘 진행 순서

1. Codex: 공통 상태·이력·검색 API와 데이터 의미 문서를 먼저 제공한다.
2. Claude: 기존 R1·R2 응답 순서/오류 보존을 마무리하고, **금액 정정 대상 / PASS의 범위 / 현재본·이전본 / 대표 판단 요약**을 수정한다. 처리 이력·서버 상태·검색도 준비된 API부터 연결한다.
3. Codex: 작은 frontend 커밋마다 병합 전에 알리고 해당 API/화면의 연속 흐름을 재확인한다. 회사 정책별 결재 역할, 같은 서류 여러 번 재발행, 부분 회신, 반려 후 재작업을 포함한다.
4. 사용자 ZIP 저장·압축 해제 확인, 현재 측정 업무함/계정·최종 측정 SHA·참가자 안내/배포 해시를 맞춘다. 내일 테스트 후 나온 문제도 같은 제품 보강 흐름에서 이어간다.

완료 목표는 다른 직원이 계약을 열어 **무엇이 문제였고, 누가 무엇을 했으며, 지금 어느 자료를 보고 다음에 무엇을 해야 하는지** 알아내는 것이다. 작은 단위별 완료와 전체 완료를 구분한다. frontend 연결·브라우저 검증 전에는 새 서버 API를 화면 완료로 보고하지 않는다.

## 지킬 데이터 원칙

- ‘원문을 정확히 읽었다’는 독립 원문 확인 기록 없이 단정하지 않는다. 금액 비교는 해당 검사 expected/actual과 금액 기준을 사용한다.
- provenance AMBIGUOUS는 동일 값의 근거 여러 곳이다. 다른 값의 충돌로 바꾸지 않는다.
- 이전본은 이미 검사에서 제외돼 있다. 같은 종류의 별도 ADD를 이전본으로 숨기지 않는다.
- 처리 이력은 기록된 사건만 보여 준다. 과거 없는 판독/확인/발송 사실은 추정하지 않는다.
- 국세청 disabled, 외부 API/자동 발송 없음. test/test2 예측·정답·평가 재실행/튜닝 없음. 가상 DEV 단위 검사만 사용한다.
- 실제 업무함·다른 세션 서버·기존 측정 과제 ZIP/정답은 보존한다. 화면 안내 문구와 배포 사본은 최종 UI 뒤에 동기화한다. 측정은 기존 담당자 과제이며 대표/지급을 무단 추가하지 않는다.
- 작은 완료 단위로 로컬 커밋한다. push·PR은 하지 않는다.

## 서버 완료·검증 기록

공통 상태·이력·검색 API와 새 사건의 snapshot 보존을 구현했다. 화면 파일은 수정하지 않았으며 화면 연결 완료와 구분한다.

- 첫 서버 전체 검사: **496개 통과, 104.92초**. 로그/리포트는 로컬 시각화 폴더의 `backend-product-work-system-full-20261005.log/.xml`이다.
- 그 뒤 지급 차단의 실제 복구 안내와 과거 결재 snapshot의 이름 가림 보완: 업무 시스템·지급·묶음 내보내기 관련 **43개 통과**.
- 이전 추출 메타데이터가 깨져도 정상 재발행을 막지 않는 보완: 업무 시스템·문서 버전 관련 **24개 통과**. 과거 값을 읽을 수 없으면 null로 기록한다.
- API의 업무 단계/기준/대기/역할이 목록·상세·review-context·별도 work-state에서 같은지 확인했다. v2→v3, 반려/재결재, 수령≠등록, 지급 후 새 자료, 커서/마스킹/한국 날짜/로그인 조건을 가상 자료로 검사했다.
- 현재 실행 중인 사용자/다른 세션 서버를 재시작하지 않았다. 새 코드로 실행한 뒤 Claude 화면 연결과 브라우저 검증이 남아 있다. UI R1·R2와 기존 UX 4건도 frontend 완료로 처리하지 않는다.
