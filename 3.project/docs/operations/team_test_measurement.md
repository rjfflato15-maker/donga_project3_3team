# 화요일 기존 방식·앱 작업시간 비교 초안

목적은 같은 난이도의 계약을 **정확히 처리하는 데 걸린 시간**을 비교하는 것이다. 과제는 **서류 누락·재발행 2개**, 한 과제·방식당 상한은 **10분(600초)**으로 고정한다. 자동 판독 정확도와 별도이며, 아직 시간 절감 실측값은 없다.

## 측정 빌드와 자료

- 측정 빌드는 **feat/ui-polish를 병합한 뒤 검증하고 사용자 확인을 마친 커밋**으로 고정한다. UI `4d71446f1b359314bf8fac73da596c2687b7656d`까지 main 병합·화면 재확인은 끝났다. 날짜를 기다릴 필요는 없다. 현재는 사용자 ZIP 실제 저장·안내문 최종 반영 전이므로 측정 SHA는 미확정이다. 백엔드 전체 449개 통과 이후 backend 변경은 없고, 최신 UI 테스트 28개·빌드가 통과했다.
- 기록할 값: main 전체 40자리 커밋 SHA, UI 브랜치의 병합 대상 SHA, 테스트·빌드 결과, 변경 파일 없는 상태, 시연 업무함 자료 버전, AI 설정·캐시 사용 여부·NTS disabled. 측정 시작 전에 채우지 못하면 측정을 시작하지 않는다. 양쪽 방식과 참가자 사이에 빌드를 바꾸지 않는다. 긴급 수정이 필요하면 새 측정 묶음으로 분리한다.
- 재발행·맡기기·ZIP은 feat/ui-polish의 연결 기능을 사용한다(사용자 전달 ff58374 포함). ZIP은 기본 가린 본, 원본은 가림 OFF와 사용자 확인 뒤 받는다. 이번 시간 과제에 맡기기·ZIP을 임의로 추가하지 않는다.
- 실제 업무와 분리한 시연 업무함과 **dev 기반 가상 자료만** 사용한다. test/test2 원문·답안은 사용하지 않는다. 앱의 분석·요청 기록은 과제마다 초기화한다. 규칙/AI 조건을 참가자 사이에서 바꾸지 않는다.
- 기존 방식에도 같은 등록 계약 금액·번호, 필수 서류 목록, 현재본·이전본 구별 정보와 업무 기준표를 제공한다. 폴더·문서 뷰어·Excel 사용을 허용하고 앱의 검수 결과·정답은 제공하지 않는다.

## 참가자와 진행 순서

1. 개발 팀원을 기본으로 하되 가능하면 **앱을 처음 보는 1명**을 포함한다. 앱 개발 참여·앱 사용 경험·기존 수작업 검수 경험을 각각 기록한다. 초보자와 개발자 결과를 구분한다.
2. 양쪽 방식의 도구와 기준표를 같은 시간으로 설명하고 측정에 쓰지 않을 연습 자료를 제공한다. 로그인·설치·자료 배치는 측정 전에 끝낸다. 5초 첫 화면 검사는 별도로 하고 작업시간에 합치지 않는다.
3. 한 참가자는 과제마다 두 방식 모두 수행한다. 절반은 기존 방식→앱, 나머지는 앱→기존 방식 순서로 배정하고 A/B 계약도 교차 배정한다. 인원이 적으면 가능한 한 균형을 맞추고 배정표를 기록한다.
4. 진행자의 시작 선언과 자료 공개부터 참가자의 완료 선언·결과 제출까지 잰다. 원문 읽기·업로드·입력·수정·앱 분석 대기를 모두 포함한다. 앱 처리 대기는 별도 기록하되 전체 시간에서 빼지 않는다.
5. 전화 등 과제 밖 중단은 양쪽 같은 기준으로 제외하고 이유·초를 적는다. 대표 접속 대기는 담당자 시간에 넣지 않는다. 도움을 줬다면 횟수·내용을 기록하고 ‘도움 없이 성공’과 구분한다.
6. **600초에 멈추고 아직 미완료면 TIMEOUT**으로 기록한다. 완료 시간을 600초로 만들어 쓰지 않는다. 상한 전에 완료했더라도 중요한 오류가 남으면 INCORRECT다.

2과제×2방식의 측정 상한은 1인당 40분이며 설명·연습은 별도다. 시간이 부족하면 참가자별로 과제를 하나만 배정하되 해당 과제는 두 방식 모두 수행한다. 측정 도중 상한을 줄이거나 미완료 기록을 삭제하지 않는다.

## 기록 양식

익명 참가자 ID를 사용한다. 실제 개인정보·비밀번호는 기록하지 않는다.

```csv
participant_id,app_developer,app_experience,manual_experience,task,variant,method,order,start_at,end_at,excluded_pause_seconds,observed_seconds,completed_seconds,machine_wait_seconds,cap_seconds,timed_out,completion_status,success_without_help,help_count,critical_error,notes,app_commit,ui_commit,dataset_version,llm_mode,nts_mode
```

- `observed_seconds = 종료 - 시작 - 과제 밖 중단`; `cap_seconds=600`.
- `completed_seconds`는 참가자가 완료를 선언한 경우만 기록한다. TIMEOUT이면 비워 두고 `timed_out=true`로 표시한다. 오답 완료는 시간과 INCORRECT를 함께 보존한다.
- `machine_wait_seconds`는 전체 관찰 시간에 포함된다. `critical_error`는 문제가 남았는데 완료·결재, 잘못된 현재본 선택, 누락 서류 오인 등이다.
- 상한을 소폭 넘겨 종료 버튼을 눌렀다면 관찰 시간은 실제 초를 남기고 요약용 제한 시간만 600초로 제한한다.

## 결과 보고와 한계

- **과제×방식별 시행 수, 성공 수, 상한 초과 수·비율, 오답 수, 도움 수, 중요 오류 수**를 먼저 표로 제시한다. 미완료를 제외해서 시간만 비교하지 않는다.
- 모든 시행에 대해 `min(observed_seconds,600)`의 중앙값·범위를 완료율과 함께 제시한다. 이는 ‘제한된 관찰 시간’이며 TIMEOUT의 실제 완료 시간이나 절감률이 아니다. 중도 포기·기기 장애는 별도 집계한다.
- 같은 참가자·과제에서 양쪽 모두 정확히 성공한 쌍의 시간 차이·절감률은 **보조 지표**로만 제시한다. 그 쌍의 수와 제외 사유를 함께 적고, 성공 쌍만 남기는 선택 편향을 명시한다. 상한 초과의 완료 시간을 추정해서 절감률을 만들지 않는다.
- 개발자는 앱에 익숙한 반면 기존 방식 실무 경험은 부족할 수 있어 앱에 유리한 편향이 있다. 순서 교차·동일 연습만으로 해소되지 않는다. 앱 초보자 1명도 이 한계를 없애지는 않는다.
- 소수 팀원·가상 자료·일회 측정과 반복 학습의 한계가 있다. 일반 회사·숙련 실무자·월 150건의 절감 효과로 확대하지 않는다. Claude 과제 안내문도 이 2과제·10분·동일 완료 기준에 맞춘다.
