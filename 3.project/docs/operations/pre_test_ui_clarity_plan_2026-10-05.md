# 10/5 팀원 테스트 전 화면 수정 인계

**최신 범위:** 사용자의 후속 지시로 [제품 기반 5개 보강+UX 수정](product_workflow_strengthening_2026-10-05.md)으로 확대했다. 아래 금액·PASS·버전·대표 UX 기준은 유지하되 ‘오늘 화면 정리에만 한정’하는 범위 제한은 적용하지 않는다. [새 공통 상태·처리 이력·검색 API](../api/work_system.md)를 함께 연결한다.

사용자 요청: 연결한 ChatGPT 대화 `파일 검토 방향`의 수정 방향을 오늘 Claude 화면 담당자와 Codex가 나누어 진행한다. 검토 기준은 main `f903aa8`(화면 `c6ac8a1`)이다. 새 기능 전체를 재구축하는 작업이 아니라 금액 정정·검사 결과·현재본·결재 판단을 명확하게 하는 수정이다.

## 확인한 것과 정정할 해석

- 사용자가 제공한 ZIP의 화면 05·06·07을 직접 열고 현재 코드와 대조했다. 첨부는 시연 복사본의 화면이며 현재 실행 서버와 동일한 상태임을 보증하지 않는다.
- **금액 정정 경로는 보완 필요:** 대조창에서 비교 기준/서류 비교값이 함께 보이지 않고 `값 고치기`가 공통 주 버튼이다. 원문과 앱 값이 같은데 계약 기준에 맞춰 앱 값을 바꾸도록 유도하지 않는다.
- **근거 ‘후보 여러 개’는 값 충돌이 아니다:** `review_context_service.py`는 현재 저장값과 일치하는 근거 위치만 반환한다. `AMBIGUOUS`는 그 위치가 여러 곳이라는 뜻이다. 동일 값의 여러 근거만으로 검사 실패나 추가 필수 확인을 만들지 않는다.
- **‘이상 없음’은 과도한 표현:** 현재 대조창은 관련 문제 0개이면 적용 검사 0개인 경우에도 초록 문구를 표시한다. 원문과 추출값의 일치, 자동 검사 통과, 사람 확인을 구분한다.
- **이전본 검사 제외는 구현돼 있다:** 명시적 REISSUE는 같은 논리 문서의 이전본을 비활성화하고 새 본만 검사/상세에 사용한다. ADD는 같은 종류여도 별도 현재 문서다. 첨부 07에서도 현재 서류 6행을 확인했다. ‘이전 견적서가 현재 검사에 섞인 결함’으로 단정하지 않는다.
- **대표 요약은 표시 보완 필요:** 현재 단계 화면에서 기존 brief 요약은 대표에게 표시하지 않는다. 기존 API로 변경 내용·현재본·남은 확인을 모을 수 있다.
- 대표 반려는 현재 코드에서 메모만 필요하고 승인용 확인 체크를 요구하지 않는다. 이 조건을 유지한다.

## 역할과 진행 순서

Claude는 `frontend/` 화면·동작·관련 회귀 검사를 수정한다. Codex는 API 의미/기준 확인, 필요한 서버 변경, 인계 문서, 작은 단위 병합과 실제 화면 재확인을 맡는다. 같은 화면 파일을 두 사람이 동시에 수정하지 않는다. 사용자는 기능별 커밋을 전달하고 마지막 ZIP 저장·압축 해제를 확인한다.

| 순서 | 오늘 수정 범위 | Claude 완료 조건 | Codex 확인 |
| --- | --- | --- | --- |
| 0 | 이미 남은 R1·R2 | 같은 계약의 낡은 조회 성공/실패 무시. 요청 패널 종료 뒤에도 409 이유 보존. 저장 결과와 새 조회 성공/실패 구분 | [기존 재현/완료 조건](../research/bundled-request-ui-audit-2026-10-05.md)의 네 오류 경계 검사 |
| 1 | 금액 비교와 정정 대상 | 계약 비교 기준·앱이 읽거나 계산한 금액·원문 근거를 함께 표시. `앱이 읽은 값 수정`과 `고친 본 올리기`의 용도를 설명 | 원문과 앱 값이 같은 실제 불일치, 실제 오독, 공급가액 기준 사례 |
| 2 | 검사 결과·근거·버전 | 어떤 검사가 일치했는지 표시. 검사 0개는 `적용된 자동 검사 없음`. 근거는 `같은 값의 근거 N곳`. 현재본 N번째·이전본 보기/비교를 명확하게 표시 | 같은 값의 여러 근거, 검사 0개, 현재본 교체·별도 ADD 구분 |
| 3 | 대표 검토 요약 | 수정 사유·서류 전후 저장값·현재본·사람 확인·남은 확인·국세청 미조회 안내를 한 상자에 표시 | 서로 다른 revision을 섞지 않는지, 자료 변경 후 재결재, 반려 이유 표시 |
| 4 | 회신 대기의 다음 행동 | 기존 요청 항목 안에서 대상 서류의 올리기/받음 기록 경로와 다음 행동을 알기 쉽게 연결. 설명·중복 진입점만 정리 | 연락·수령·등록·검사 통과를 구분하고 부분 수령 후 나머지 대기 유지 |

1~3은 오늘 우선 처리한다. 4는 기존 상태와 API를 유지하는 범위에서 진행한다. 표의 번호는 연결한 리뷰의 UX 번호와 다르다. 각 묶음 완료 시 frontend 변경 파일·커밋·실행 검사·직접 확인한 경로를 전달한다. Codex는 병합 전에 알리고 관련 경로를 확인한다. push·PR은 만들지 않는다.

## 기존 API로 연결할 데이터

새 API는 현재 수정의 선행 조건이 아니다. 없는 값은 추정하지 않고 `확인 기록 없음` 또는 `불러오지 못함`으로 표시한다.

| 목적 | 현재 데이터 | 의미/주의 |
| --- | --- | --- |
| 금액 비교 | 상세/대조창의 `checks[].rule_id`, `field`, `status`, `expected`, `actual`; `workflow.amount_basis` | 해당 문서·해당 금액 검사 기준을 사용. 공급가액 계약의 합계 비교는 등록 공급가액+명시 세액일 수 있다. 등록 금액을 무조건 합계 비교값으로 쓰지 않는다. |
| 원문 근거·사람 확인 | `GET /api/contracts/{id}/review-context`의 `documents[].fields` | `value`, `source`, `evidence_status`, `evidence[]`, `human_confirmation` 활용. 독립 판독값이 따로 있는 것은 아니다. 근거 위치만으로 ‘AI가 정확히 읽었다’고 단정하지 않는다. |
| 현재본 | 계약 상세 `documents[].version` | `logical_document_id`, `version_number`, `is_current`, `previous_document_id`. 같은 종류의 별도 ADD를 숨기거나 REISSUE 이력과 합치지 않는다. |
| 변경 사유·등록자·이전본 | `GET /api/documents/{id}/versions` | `change_note`, `actor_name`, `uploaded_at`, 버전별 `fields`. 등록자와 필드 확인자를 구분한다. 이전본은 조회만 하며 정정/교체의 대상으로 자동 선택하지 않는다. |
| 서류 전후 값 | `GET /api/documents/{id}/compare` | `comparison_basis=CURRENT_SAVED_FIELDS`: 이전 서류 본과 현재 서류 본의 **저장값** 비교다. 원문 독립 판독이나 이전 결재 당시 비교로 표현하지 않는다. |
| 현재 상태 요약 | `GET /api/contracts/{id}/summary?style=brief` | 금액 기준·서류 종류 수·미확인·결재 상태·revision/fingerprint·검사/카드 수. 변경 사유나 확인자는 이 응답에 없으므로 다른 응답과 결합한다. |

요약과 비교 조회는 계약 ID·revision/fingerprint 기준으로 최신 세대만 반영한다. 문서 변경 때 이전 요약을 새 자료의 요약처럼 표시하지 않는다. 비교 실패는 `변경 없음`으로 바꾸지 않는다. 기존 개인정보 가림을 요약·사유·전후 값에도 적용한다.

`amount`와 `total_amount`가 동일한 전후 변화를 중복 표시하면 의미가 같은 경우만 하나로 모은다. 공급가액·세액·합계의 서로 다른 변화를 삭제하지 않는다. 별도 원문 후보 전체나 서로 다른 후보값 개수는 현재 evidence API에 없으므로 만들어 표시하지 않는다.

## 금액 경로 완료 예시

합계 기준 계약으로 다음 세 사례를 구분한다.

1. 계약 200만원 / 원문 190만원 / 앱 190만원: 앱 190만원을 유지하고 계약 불일치는 남긴다. 원문 확인 후 거래처 보완 요청 또는 등록 기준 확인으로 안내한다.
2. 계약 200만원 / 원문 190만원 / 앱 오독 180만원: 원문 확인 후 190만원으로 정정해도 계약과의 불일치는 남는다. ‘계약에 맞추기’ 자동 입력은 없다.
3. 같은 190만원이 원문 두 곳에 있는 경우: `같은 값의 근거 2곳`으로 안내한다. 이 개수만으로 금액 충돌이나 검사 실패로 바꾸지 않는다.

원문이 잘못된 경우와 등록한 계약 기준이 잘못된 경우를 앱이 자동 판정하지 않는다. 등록 기준 수정은 기존 별도 수정·사유·revision 경로를 사용한다. 필드 정정의 원문 확인·사유 조건을 유지한다.

## 오늘 마무리와 내일 테스트

- 기능별 수정/관련 검증 → 사용자 ZIP 실제 저장·압축 해제 확인 → 최종 측정 커밋 확정 → 최신 서버/계정 안내 → 참가자 안내의 최종 버튼 문구·배포 사본·해시 동기화 순서다.
- 기존 R1·R2와 이번 새 수정은 서로 구분한다. 완료한 B1~B5를 다시 미완료로 세지 않는다.
- test/test2 예측·정답·평가·모델/가드와 측정용 과제/정답 ZIP을 변경하거나 재실행하지 않는다. 국세청 disabled, 외부 API 추가 없음, 실제 업무함 변경 없음.
- 내일의 기존 시간 측정은 담당자 과제다. 대표 결재·지급을 시간 과제에 추가하지 않는다. 대표 화면은 별도 사용성 확인으로 볼 수 있다.
- 검색은 최신 제품 보강 범위에 포함한다. 건수는 계약/서류 종류/검사 항목/문제 묶음 단위를 명시하며 실제 개인 배정 필터 없이 `내 담당 계약`이라고 바꾸지 않는다.
