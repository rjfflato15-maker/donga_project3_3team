# 등록·원문 확인·보완·결재·지급 흐름

> 상태: 현재 기준
> 확인일: 2026-10-10
> 기준: HEAD `54a8841` + 미커밋 작업 트리. 작업 트리 기준. 설치 검증 범위는 고객 패키지 안내 참조.

관련 소스: [ContractStageView.tsx](../../frontend/src/components/review/ContractStageView.tsx) · [DocumentWorkspace.tsx](../../frontend/src/components/review/DocumentWorkspace.tsx) · [useAutoRefresh.ts](../../frontend/src/hooks/useAutoRefresh.ts) · [workflow_service.py](../../backend/app/services/workflow_service.py)

1. 계약 기준(거래처·금액 의미·지급 방식)을 등록하고 서류를 업로드한다. 0/null, 공급가액/합계, 현재 본과 이전 본을 구분한다.
2. 자동 검사 결과와 현재 서류의 원문을 대조한다. 원문과 같은 값도 선택한 필드만 사람 확인으로 기록한다. 계약 기준과 다른 값은 원문 확인만으로 PASS가 되지 않는다.
3. 판독이 어렵다면 선명한 고친 본을 받거나 현재 쪽 VLM 재판독을 사용한다. 후보는 실제 원문과 대조한 항목만 저장한다. 읽히지 않는 금액을 계산해서 채우지 않는다.
4. 거래처에 필요한 외부 보완 항목을 선택해 문구를 만들고 복사한다. 평소 메일/메신저로 실제 연락한 뒤 요청 이력을 기록한다. 앱이 외부 메일을 발송하는 기능은 없다.
5. 받은 항목과 기다리는 항목을 각각 기록한다. 파일 등록·회신 수령과 자동 검사 통과를 구분한다. 재발행은 이전 본을 보존하고 현재 자료 기준으로 재검사한다.
6. 담당자가 필수 원문 대조·회신 처리를 끝내고 검토 의견을 적어 **검토 완료·결재 상신**을 누른다. 서버가 현재 자료·검토 차수와 연결해 저장한 뒤 대표 결재 대기로 바뀐다. 단일 대표 정책에서도 담당자 상신이 필요하며, 2단계 정책의 담당 검토는 같은 상신에 연결된다. 대표가 사유를 남겨 승인하거나 반려한다. 반려·자료 변경 뒤에는 재검토·재상신한다.
7. 실제로 송금한 뒤 계약 전체 지급 완료 사실을 기록한다. 앱에서 은행 송금을 실행하지 않는다. 이전 지급이 있으면 중복 송금 대신 같은 지급의 현재 연결을 확인한다.
8. [정산 XLSX·증빙 ZIP](accounting_export.md)을 확인해 세무 담당자에게 전달한다.

업무함은 표시 중인 탭에서 10초마다 목록·건수를 조회하고 다시 표시되면 즉시 조회한다. 상세 입력은 덮어쓰지 않으며 다른 곳의 변경이 있으면 최신 내용 확인 안내를 보여 준다. “지금 갱신”과 상세의 최신 자료 불러오기를 구분한다.

회사별 결재 순서·판정은 서버가 기준이다. 화면의 간단한 다음 행동 문구를 새로운 승인·지급 권한으로 해석하지 않는다. 자세한 상태 계약은 [API 안내](../api/README.md)와 [자동 검사 정책](../validation/current_rules.md)을 따른다.

## 잘못 기록한 업무 복구

등록 파일 처리 실패 시 ‘실패한 서류 다시 처리’로 같은 계약에서 이어 처리하거나 ‘등록한 계약 확인’으로 보완한다. 선택한 종류와 계약 금액 기준은 등록 시 함께 저장한다.

계약을 잘못 제외했다면 계약 찾기 → 제외한 계약 보기 → 업무함으로 복원한다. 서류·요청·결재·지급 기록이 유지된다. 회신 수령·취소를 잘못 기록했다면 요청 내역의 서류별 ‘회신 기록 정정’에서 사유를 적고 상태를 정정한다. 지급일·방법·메모 또는 잘못된 지급 완료는 더보기 → 지급 기록 정정에서 처리한다. 취소는 실제 송금 취소가 아니며 실제 거래 내역 확인 후 새 지급 사실을 기록한다.

## 청구액과 지급 완료 구분

계산서 원문 화면은 청구액·계약 총액과 계약의 지급 기록을 따로 표시한다. `잔금`은 지급 회차 표현이며 단독으로 일부 청구나 완납을 뜻하지 않는다. 계약서의 회차·비율·금액과 계산서 금액이 다른 경우 원문 계약 조건과 이전 청구 여부부터 확인한다. 외상미수금을 청구액에 다시 더하지 않는다.

현재 일괄 정산 시연은 선금 없이 최종 검수 후 공급가액 3,500만원 + 세액 350만원 = 총 3,850만원을 한 번에 청구하는 조건이다. 계약서·견적서·계산서·검수확인서를 수정본으로 등록했고, 이전 원본과 이력은 보존했다. 지급 완료 기록은 만들지 않았으므로 검수·대표 결재 후 실제 송금 사실을 별도로 기록하는 흐름으로 시연한다. 문서상의 2026년 10~12월 날짜는 합성 시연 일정이다.

## 상신 전에 확인할 이유와 다음 행동

| 화면의 이유 | 담당자가 할 일 | 대표에게 넘길 수 있는 조건 |
| --- | --- | --- |
| 읽지 못함·원본 검증 실패 | 원본 복구 또는 읽을 수 있는 수정본 등록·재검사 | 전체 원본과 판독 근거 확보 |
| 서류 누락 | 빠진 종류를 요청하고 파일 등록 | 필수 종류 확보 |
| 원문 대조 미완료 | 표시한 서류·필드를 열어 원문과 같음 또는 오독 정정 | 필수 필드의 현재 확인 기록 |
| 실제 불일치·미확인 | 보완·정정 또는 근거를 남긴 예외 판단 요청 | 기술 실패 없이 전체 예외 항목·사유 명시 |
| 거래처 회신 대기 | 받은 항목만 수령 기록, 나머지는 대기 | 현재 요청의 미회신 해소 |
| 대표 결재 대기 | 담당자 상신 이력 확인, 대표가 승인·반려 | 현재 상신본과 같은 자료·검토 차수 |

자동 PASS, 문제 없음 판단, 요청 문구 복사만으로 담당자 원문 확인이나 상신을 대신하지 않는다. 기술 실패·필수 서류/원문 검토 누락·회신 대기는 예외 문구로 우회할 수 없다. 업무상 불일치 예외는 담당자 사유와 항목을 저장하고 대표가 별도 확인·근거를 남겨 판단한다.

상신 버튼 중복 클릭은 같은 요청 키로 한 번만 저장한다. 새로고침으로 이력이 사라지지 않으며, 반려 뒤 오래된 화면의 상신·승인은 최신 차수를 확인하라는 충돌로 거부한다. 자료 변경 전 결재와 지급 기록은 보존한다.
