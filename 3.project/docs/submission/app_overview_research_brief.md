## 1부. 우리 앱은 무엇인가

### 한 줄 정의

**계약별 증빙 서류를 분류하고 핵심 값을 구조화해 등록한 계약 기준과 대조하며, 사람이 원문을 확인하고 보완 요청·회신·재발행·결재·지급 기록을 이어서 관리하는 로컬 실행 업무용 시제품.**

외주 대금 지급 전 증빙 검토를 대상으로 한다. 회계·인사·재고를 모두 처리하는 ERP 전체가 아니라, **계약 증빙 검수와 처리 기록**을 구현한 프로젝트다. 기본 증빙은 6종이고 회사 설정에서 필수 종류를 바꿀 수 있다.

### 사용자와 시범 가정

| 대상 | 하는 일 |
| --- | --- |
| 담당자 | 서류 등록, 원문 확인·값 수정, 거래처 보완 요청 문구 작성, 요청·부분 회신 기록, 재발행본 등록, 지급 사실 기록 |
| 대표 | 검수 결과·변경 내역·담당 의견을 보고 최종 결재 또는 반려, 직원 계정 관리 |
| 세무사·회계 프로그램 | 앱 밖에서 정산 XLSX와 증빙 ZIP을 받아 회계 업무 처리 |

직원 6명, 실무 담당자 1명, 대표 1명, 월 약 150건은 **시범 설계 가정**이다. 실제 고객 수요 조사나 월 처리량 성능 측정 결과가 아니다.

대표 1단계 결재와 **담당 검토 → 대표 결재의 2단계 흐름이 실제 구현**돼 있다. 지원 정책의 최대 단계 수는 2개다. 3~5인 자유 결재선·병렬 결재·대결을 지원하는 제품으로 설명하지 않는다.

### 다루는 서류와 색인의 의미

기본 서류는 계약서·견적서·사업자등록증·통장사본·세금계산서·검수확인서다. PDF·이미지·DOCX·HWP/HWPX 등의 판독 경로가 있다. 모든 형식·스캔 품질에서 판독 성공이나 같은 원문 배치를 보장하지 않는다.

본문 추출 또는 OCR 뒤 서류 종류를 분류하고, 상호·사업자번호·공급가액·세액·합계·발행일·은행·계좌번호 등의 값을 구조화한다. **통장사본의 예금주와 등록한 계약 거래처명 대조도 구현돼 있다.** 법인 표기·공백·일부 문장부호를 정리한 이름이 같으면 PASS, 다르거나 못 읽으면 REVIEW로 남긴다. 개인사업자 대표자 명의 가능성을 사람이 확인하며, 유사도·부분 일치로 PASS 처리하지 않는다. 은행의 실제 계좌 소유자 인증이나 계약서 원문 전체의 당사자 조항 해석을 뜻하지 않는다.

여기서 색인은 계약 ID·서류 종류·문서 버전·추출 필드·원문 근거를 연결해 정리하는 의미다. 문서 전체에 대한 의미 검색·RAG 질의응답까지 구현했다고 표현하지 않는다.

### 현재 화면의 업무 흐름

```text
서류 선택 → 종류·값 자동 판독 → 계약 기준 확인·등록 → 자동 검사
                                                       ↓
                                              원문과 저장값 확인
                                                       ↓
                    ┌──────────────────────────────────┼─────────────────────────┐
                    ↓                                  ↓                         ↓
              거래처 서류 문제                     앱 판독·사내 문제          검토 후 결재
              묶음 요청 문구 작성                  원문 확인·값 수정          정책에 따른 차례
              외부에서 직접 발송                         ↓                         ↓
              요청 기록·부분 회신                  다시 자동 검사           대표 승인·반려
              새 서류·고친 본 등록                                                  ↓
              새 파일 판독·재검사                                               지급 사실 기록

정산 XLSX·증빙 ZIP은 필요한 시점에 내보낸다.
미확인 상태도 함께 담기므로 다운로드 자체가 검수·결재 완료를 뜻하지 않는다.
```

| 과정 | 실제 동작과 경계 |
| --- | --- |
| 서류 선택·기준 등록 | 받은 서류를 선택하고 읽어 온 거래처·사업자번호·금액을 확인한다. 계약 금액의 부가세 포함 여부와 일시/분할 지급 기준을 등록한다. 읽어 온 값 자체를 정답으로 간주하지 않는다 |
| 자동 검사 | 현재 본의 저장값과 등록한 계약 기준으로 PASS / FAIL / REVIEW / MISSING을 계산한다. 서류 종류 수와 파일 수를 구분한다 |
| 원문 확인 | 저장값·출처·원문 근거·자동 검사·사람 확인을 나눠 보여 준다. 한 번 확인과 10초 되돌리기, 다음 항목 이동을 지원한다. 값 하나 확인을 문서 전체 확인으로 바꾸지 않는다 |
| 판독 보완 | 잘못 읽은 값은 원문에 맞게 수정한다. PDF·이미지는 버튼으로 로컬 VLM 재판독을 요청할 수 있다. 후보 가운데 사람이 선택한 값만 저장한다 |
| 거래처 보완 요청 | 빠진 서류와 원문 확인을 거친 불일치 항목을 문구 하나로 묶는다. 사용자가 카톡·메일 등으로 직접 보낸 뒤 사내 기록을 남긴다. 실제 발송·수신 자동 연동은 없다 |
| 부분 회신·재발행 | 받은 항목만 수령 기록하고 나머지는 대기로 남긴다. 고친 본은 같은 논리 문서의 다음 버전으로 등록하고 이전 본을 보존한다. 수령 기록과 검사 통과는 별개다 |
| 결재·반려 | 현재 정책의 역할·차례를 따른다. 필수 서류나 원본 누락은 승인을 막는다. FAIL·REVIEW가 남아도 확인 동의와 10자 이상 의견으로 승인할 수 있으므로, 모든 문제를 자동 차단한다고 설명하지 않는다 |
| 자료 변경 후 재확인 | 자료 버전·지문과 과거 결재를 대조한다. 자료가 달라지면 이전 승인 기록을 지우지 않고 현재 자료의 결재를 다시 요구한다. 원문 확인·회신 수령·결재는 서로 다른 기록이다 |
| 지급 기록 | 실제 송금은 앱 밖에서 한다. 앱은 현재 자료의 최종 결재와 원본 해시를 확인한 뒤 계약 전체 지급 완료 사실을 기록한다. 분할 지급의 회차별 송금 관리가 아니다 |
| 이미 지급한 계약 변경 | 기존 지급 사실을 보존하고 재확인을 요구한다. 조건이 맞으면 같은 지급으로 재확인하며 새 지급을 만들지 않는다. 거래처·금액 등 지급 범위가 달라지면 재확인이 막힐 수 있다 |
| 내보내기 | 정산 XLSX 5시트와 현재·이전 증빙 및 이력 ZIP을 제공한다. 특정 ERP 전표 양식의 자동 업로드 호환성을 검증한 것은 아니다 |

표시 중인 업무함은 기본 약 10초 간격으로 조회하고, 숨겨진 탭은 조회를 멈춘다. 다른 사용자의 변경 안내와 오래된 자료로 저장하는 충돌 처리를 지원한다. 즉시 전달되는 WebSocket·Push 알림으로 설명하지 않는다.

### 자동 검사와 업무 통제의 범위

| 항목 | 구현 범위 | 해석할 때 지킬 것 |
| --- | --- | --- |
| 필수 서류 | 회사 정책의 필수 종류 누락 | 기본 6종이며 모든 회사에 6종을 강제하지 않음 |
| 원본·판독·분류 | 원본 없음, 처리 실패, 미분류를 확인 대상으로 표시 | 내용 판독 성공이나 문서 진위를 보장하지 않음 |
| 사업자번호 | 계약서·견적서·세금계산서·사업자등록증의 번호와 등록 기준을 비교 | 사업자 실제 상태나 세금계산서 진위 인증과 별개 |
| 예금주 이름 | 통장사본의 추출 예금주와 등록한 계약 거래처명을 정규화해 비교 | 불일치·미추출은 REVIEW. 실제 계좌 소유 진위 인증이나 계약 당사자 법률 판단이 아님 |
| 계약 금액 기준 | 부가세 포함 합계 또는 공급가액+등록한 세액 | 기준이 불분명하면 확인 필요. 세액을 임의로 10% 역산하지 않음 |
| 문서 내부 금액 구성 | 견적서·세금계산서의 공급가액+세액과 표시 합계 대조 | 모든 서류의 모든 금액을 검사하는 것은 아님 |
| 계약 기준 금액 대조 | 견적서·세금계산서 금액을 계약 합계 기준과 비교 | 부분 청구·청구 범위 미확인은 별도 확인 |
| 분할 청구 | 분할 지급 정책에서 부분 청구·누적 합계 확인 | 누적액이 계약보다 작거나 의미가 불명확한 경우도 확인 대상으로 남음 |
| 동일 계산서 파일 중복 | 분할 지급 검사에서 현재 세금계산서 파일의 동일 해시 확인 | 재스캔·재촬영한 다른 파일이나 의미상 중복까지 찾는 기능은 아님 |
| 결재·지급 연결 | 자료 revision·fingerprint·원본 해시로 이전 기록과 현재 자료의 연결 확인 | 과거 승인·지급 사실을 삭제하거나 실제 지급을 취소하지 않음 |
| 국세청 사업자 상태 | 현재 pilot·평가에서는 disabled 유지, 실제 조회 미수행 안내 | 활성 검수 기능 목록이나 세금계산서 진위 검증으로 세지 않음 |

정확한 정책은 [현재 검수 규칙](../validation/current_rules.md)을 따른다. 핵심은 **등록 기준과 서류의 대조, 서류 내부 계산 확인, 분할 청구 누적 확인**이다. 6종 서류의 모든 문장·값을 서로 교차 검증하는 시스템으로 설명하지 않는다.

### AI 역할: 두 경로를 구분

| 경로 | 입력·역할 | 저장과 사람 확인 |
| --- | --- | --- |
| 텍스트 LLM 보완 | 활성화된 경우 본문/OCR에서 규칙이 해결하지 못한 대상 칸을 Qwen3 등의 로컬 모델로 보완 | 원문 근거 가드를 통과한 값은 저장 필드에 자동 반영된다. 사람 확인 완료와는 별개이며, 원문 대조·수정·확인 기록을 지원한다 |
| 이미지 VLM 재판독 | 사용자가 버튼을 눌러 현재 PDF 쪽·이미지를 설치된 로컬 비전 모델로 다시 읽음 | 형식 등을 확인한 후보를 보여 주며 자동 반영하지 않는다. 사람이 원문을 보고 선택한 값만 저장한다 |
| 규칙 검사 | 등록 기준·저장값·현재 본으로 금액·번호·누락을 계산 | LLM이 PASS/FAIL을 직접 결정하지 않는다. 사람 확인이나 결재가 불일치 검사를 PASS로 덮어쓰지 않는다 |

직접 실행의 텍스트 LLM은 기본 비활성이며 실행 경로·설정과 모델 준비 상태를 확인해야 한다. Qwen2.5-VL 등의 재판독도 해당 이미지 모델이 설치·준비돼 있어야 한다. AI가 꺼져 있거나 호출이 실패한 경우의 규칙 처리·확인 안내를 AI가 성공한 것으로 세지 않는다. 설정은 [AI 실행 기준](../ai/runtime_settings.md)에 따른다.

### 로컬 실행·정보 관리·운영

- 앱 서버·DB·선택한 로컬 AI 모델을 서버 PC에 두고, 다른 직원은 사내망 브라우저로 접속하는 구성을 대상으로 한다. 현재 AI 호출 코드는 loopback의 설치된 Ollama 모델을 사용하며 문서를 외부 클라우드 AI에 전송하는 경로를 사용하지 않는다.
- 초기 런타임·모델 준비에는 다운로드가 필요할 수 있다. 사내망 실행을 초기 준비까지 인터넷이 필요 없는 완전한 망분리 설치 검증으로 표현하지 않는다.
- 개인정보 가림은 화면·원문 미리보기·내보내기와 실제값 입력·외부 요청 문구에서 범위가 다르다. 자동 원문 가림의 누락 가능성이 있고, 외부에 보낼 문구에는 업무에 필요한 실제값이 들어갈 수 있다. 자세한 범위는 [내보내기](../operations/accounting_export.md)와 [화면/API 연결](../api/frontend_integration.md)을 따른다.
- 담당자·대표 권한 분리, 직원 계정 비활성화, 처리자·사유·값 변경 이력, 백업·복원을 지원한다. 모든 기업 보안·인증 요건을 충족한 상용 제품이라고 주장하지 않는다.
- 소스 실행·가상 업무함의 연결·회귀 검증과 이전 버전의 고객 Setup 격리 설치 기록을 구분한다. 이번 배포는 소스 전용이며 현재 소스의 Windows 실행·Setup 재빌드·실제 AI 준비는 검증하지 않았다. [현재 상태](../progress/current_status.md)에서 구현·검증·남은 일을 구분한다.

### 평가 결과와 발표에서 말할 수 있는 범위

아래는 **고정된 v4 test2의 합성 자료 평가**다. 현재 작업 트리의 모든 신규 기능이나 실제 고객 업무 정확도를 대표하지 않는다.

v3 dev·v3 test·v4 test2는 자료·가드·분모가 달라 개선 추이로 이어 붙이지 않는다. 상세 수치·정답 출처·제한은 [평가 요약](evaluation_results.md)과 [test2 원본](../eval/test2/final_four_modes.md)을 따른다.
