# C Pilot 발표 스토리라인과 근거 준비

> 상태: 초안 — 발표 구성·근거 수집 계획, 최종 슬라이드·확정 대본 아님
> 확인일: 2026-10-09
> 기준: 2026-10-09 구조 정리 소스 사본. 현재 소스와 과거 설치·평가 기록의 검증 범위를 구분한다.

발표의 중심 질문은 **“서류에서 읽은 값이 계약과 다를 때, 무엇을 고쳐야 하고 어떤 근거를 남겨야 할까?”**다. 가상 계약 한 건을 따라가며 분류·색인, 원문 확인, 보완 요청, 재발행, 결재가 어떻게 연결되는지 보여 준다. AI 추출 결과와 사람 확인, 요청 수령, 결재를 각각 구분한 설계와 실제 검증을 프로젝트 성과로 설명한다.

시장 비교는 기존 제품의 존재와 역할을 설명하는 한 장으로 제한한다. 사업성·독창성은 검증할 가설이며, 기존 제품에 기능이 없다는 주장이나 측정하지 않은 시간 절감을 발표의 전제로 삼지 않는다. 현재 구현 범위는 [앱 소개·리서치 브리프](app_overview_research_brief.md), 수치는 [평가별 결과](evaluation_results.md)를 기준으로 한다.

## 1. 발표를 관통할 이야기

### 시작: 숫자를 고치는 것이 해결일까?

첫 사례는 가상 새봄기획의 업무지원 시스템 구축 계약이다. 계약 기준은 부가세 포함 **3,410,000원**, 견적서에 표시된 합계는 **3,520,000원**으로 110,000원 차이가 난다. 공급가액과 합계를 혼동한 사례로 설명하지 않도록 두 값의 의미를 화면에 명시한다.

> “계약 기준은 341만 원인데 견적서에는 352만 원이 적혀 있습니다. 앱에 저장된 값을 341만 원으로 바꾸면 해결될까요? 계약 기준을 확인했고 원문도 352만 원이라면, 거래처에서 고친 견적서를 받아야 합니다. 저희는 이 판단부터 보완·재확인·결재까지 이어지는 과정을 구현했습니다.”

실제 고객 사례가 아니라 시연용 합성 자료다. 거래처 서류에 문제가 있다는 판단은 발표자가 등록한 계약 기준과 원문을 확인한 뒤에 한다. 모델이 읽은 숫자만으로 거래처 오류를 단정하지 않는다. 등록 기준이 잘못됐을 가능성도 확인한다.

### 중간: 콘텐츠 분류·색인이 업무로 이어지는 과정

프로젝트 주제인 콘텐츠 자동 분류·색인을 계약 증빙에 적용했다. 종류를 나누고 핵심 값을 구조화한 뒤 계약·문서 버전·원문 근거와 연결한다. 등록 기준과의 대조 결과를 사용자가 원문에서 확인하고, 거래처 서류 문제와 앱 판독 문제를 구분해서 처리한다.

서류를 받았다는 기록은 검사 통과가 아니고, 자동 검사 통과는 사람 확인이나 대표 결재가 아니다. 이 구분이 요청·부분 회신·재발행·결재 화면에서도 유지되는 것을 보여 준다.

### 전환: 결재한 뒤 서류가 바뀌면?

승인 뒤 자료가 바뀌는 짧은 예외 사례를 보여 준다. 이전 승인 이력은 보존하지만 현재 자료에 대한 결재는 다시 요구한다. 이미 지급한 계약이라면 기존 지급 사실을 보존하고 같은 지급의 재확인 여부를 판단한다. 앱이 실제 송금하거나 자동으로 다시 지급하는 기능은 아니다.

### 끝: 구현 결과와 검증에서 배운 것

“정확도가 높으므로 맡겨도 된다”로 끝내지 않는다. 네 조건 비교에서 무엇이 좋아졌고 무엇이 나빠졌는지, 가드가 정답 제안도 보류한 이유, 작은 VLM 연결 시험에서 가린 숫자를 추측한 사례를 설명한다. 마지막에 처음 질문으로 돌아온다.

> “저희가 구현한 것은 계약 증빙을 분류하고, 읽은 값의 근거를 확인하며, 보완과 재결재까지 처리 기록을 이어 주는 시스템입니다. 실제 고객의 시간 절감과 도입 가치는 다음 검증 과제로 남겨 두었습니다.”

## 2. 과제 기준과 발표에서 보여 줄 증거

첨부된 「3차 프로젝트 안내사항」의 프로젝트 자가진단 기준을 구성 근거로 사용한다. 아래 비중은 안내문 기준이며 점수 획득을 보장하는 표가 아니다. 안내문에 발표 제한 시간이 명시돼 있지 않아 다음 장의 시간은 리허설 제안이다.

| 안내문 기준 | 비중 | 발표에서 보여 줄 것 |
| --- | --- | --- |
| 기술 설계·AI/Agent 활용 | 35% | 요구사항, 시스템·데이터 흐름, 분류·색인 구조, 규칙/텍스트 LLM/VLM의 역할, 불확실한 결과 처리 |
| 서비스 구현·안정성 | 30% | 실제 앱의 입력→처리→출력, 원문 확인 UX, 보완·회신·재발행, 잘못된 입력·호출 실패·권한·자료 변경 처리 |
| 검증·개선·문제 해결 | 20% | 고정 예측과 재채점, 네 조건 비교, 실패 원인과 개선, 실행·운영 재현성, 검증 한계 |
| 발표·문서·과정 | 15% | 구현과 일치하는 설명·흐름도, 실제 팀원 역할, 문제 해결 과정, 팀원 후기 |

팀원 역할과 후기는 필수 항목이다. 발표 준비 업무를 실제 개발 기여로 대신 적지 않는다. 사업계획·가격·시장 독점은 이 안내문에서 필수 발표 항목으로 확인되지 않았으므로 본문을 압도하지 않게 한다.

## 3. 장표별 구성: 15분 리허설 제안

14장, 설명·시연 합계 **14분 15초 + 전환 여유 45초** 제안이다. 공식 발표 시간이 확인되면 먼저 줄일 것은 시장 설명·부가 기능 나열이고, 팀 역할·검증 한계·핵심 업무 시연은 유지한다. 질의응답 시간은 별도다.

| 장 | 제목과 핵심 메시지 | 화면·증거 | 제안 시간 |
| --- | --- | --- | --- |
| 1 | C Pilot: 계약 증빙의 분류·색인부터 검토 기록까지 | 앱 이름·팀·프로젝트 주제 | 15초 |
| 2 | 이 숫자를 계약 금액으로 바꾸면 해결될까요? | 같은 의미의 계약 기준 341만 원 / 견적 합계 352만 원 | 45초 |
| 3 | 파일을 읽은 뒤에도 남는 업무를 연결했습니다 | 서류 선택→판독·분류→기준 등록→검사→사람 확인→보완→결재 흐름도 | 45초 |
| 4 | 기존 ERP·경리·결재 도구와 비교한 구현 범위 | 공식 자료가 확인되는 가까운 대체 수단 3개, 확인 불가 칸 표시 | 45초 |
| 5 | 값·근거·문서 버전을 어떻게 연결했나 | 브라우저/API/DB·원본/Ollama 구성도와 계약→문서 버전→필드·근거 관계 | 60초 |
| 6 | 규칙, 텍스트 LLM, 이미지 VLM의 역할이 다릅니다 | 두 AI 경로 도식, 실제 후보·근거·사람 선택 화면 | 90초 |
| 7 | 한 계약의 누락과 금액 불일치를 처리해 봅니다 | 실제 앱: 원문 확인→3항목 묶음 요청→2항목 수령→고친 견적서→대표 검토 | 180초 |
| 8 | 승인한 뒤 자료가 바뀌면 다시 확인합니다 | 승인→자료 변경→현재 승인 무효→재결재. 지급 후 변경은 짧은 별도 화면 | 60초 |
| 9 | 실패·충돌·권한·개인정보를 처리한 방법 | 두 탭 충돌, 업로드 실패 재시도, 역할 차례, 가림 범위 중 대표 2개 | 45초 |
| 10 | AI 효과를 네 조건으로 비교했습니다 | test2 네 조건 정확도, 분모·정답 출처·평가 한계 | 90초 |
| 11 | 가드가 정답도 막았던 실패에서 배웠습니다 | v3 test의 보류 원인, 가드 없는 조건과의 차이, 별도 VLM 오답 사례 | 60초 |
| 12 | 구현한 운영 기능과 다음 검증 | XLSX/ZIP·백업 범위, 현재 소스의 Windows 설치 미검증, 실무 효과 측정 계획 | 45초 |
| 13 | 팀 역할과 프로젝트에서 배운 점 | 실제 이름·담당 산출물·해결한 문제·팀원 후기 | 60초 |
| 14 | 읽은 값의 근거와 이후 처리를 이어 남겼습니다 | 처음 사례의 요청·고친 본·확인·결재 기록으로 마무리 | 15초 |

2·7·8·14장은 같은 가상 계약을 사용한다. 장표마다 새로운 회사·금액을 등장시키면 업무 흐름이 끊긴다. 긴 기능 목록은 부록으로 옮기고 본문에는 그 기능이 해결한 상황을 보여 준다.

## 4. 대표 시연: 같은 계약 한 건으로 준비

### 자료와 시작 상태

- 가상 거래처: 새봄기획. 계약 기준: 부가세 포함 3,410,000원, 일시 지급.
- 기본 6종 중 계약서·견적서·사업자등록증·검수확인서 4종 준비. 통장사본·세금계산서는 처음에는 빠져 있다.
- 최초 견적서 합계 3,520,000원, 고친 견적서 합계 3,410,000원. 같은 합계 항목끼리 비교한다.
- 부분 회신은 통장사본·세금계산서 2종, 마지막 회신은 고친 견적서다. 거래처 요청 3항목과 서류 종류 누락 2종을 혼동하지 않는다.
- 측정·고정 평가 자료와 분리된 가상 시연 업무함을 사용한다. 실제 거래처 정보와 계정 비밀번호는 장표·영상에서 제외한다.

### 시연 순서와 말할 내용

| 순서 | 실제 동작 | 보여 줄 차이·발표 멘트 |
| --- | --- | --- |
| 1 | 4종 서류 판독·분류 후 계약 기준을 확인하고 등록 | “읽어 온 값 자체가 정답은 아닙니다. 계약 기준을 확인해 등록합니다.” 시간이 길면 사전 녹화로 시작하고 처리 완료 상태부터 실제 앱으로 이어 간다 |
| 2 | 필요한 6종 / 받은 4종 / 빠진 2종과 금액 불일치 확인 | 파일 개수와 서류 종류 수를 구분하고, 계약 기준과 저장값의 의미를 나란히 보여 준다 |
| 3 | 견적서 원문 합계와 현재 저장값 비교 | 원문도 352만 원임을 사람이 확인한다. 잘못 읽었을 때의 값 수정과 잘못된 서류를 교체하는 처리를 구분한다 |
| 4 | 누락 2종+견적서 정정 1건을 문구 하나로 묶어 기록 | 연락 방법·기한·기록을 한 번에 처리한다. 앱은 문구와 기록을 만들며 실제 외부 발송은 사용자가 한다 |
| 5 | 통장사본·계산서를 추가하고 받은 2항목만 기록 | 받은 2건 / 기다림 1건을 보여 준다. 수령만으로 검사·결재 완료가 되지 않는다 |
| 6 | 같은 견적서의 고친 본을 업로드하고 전후 비교 | 3,520,000→3,410,000원. 이전 본 보관, 새 본 재판독·재검사, 현재 본 원문 확인을 보여 준다 |
| 7 | 대표 역할로 검토 요약·현재 본·변경 이력을 보고 결재 | 현재 결재 정책의 차례를 따른다. 자동 검사 결과와 사람 확인·최종 결재를 나눠 보여 준다 |
| 8 | 결재 뒤 자료를 바꾸고 이전 승인 상태 확인 | 과거 승인은 기록으로 남고 현재 자료에는 재결재가 필요하다 |

예금주 대조는 부분 회신으로 올라온 통장사본에서 한 번 보여 준다. 등록 거래처명과 추출 예금주를 정규화해 비교하는 규칙이며, 다르거나 못 읽으면 REVIEW다. 은행의 실제 계좌 소유 인증이나 계약서 전체의 법적 당사자 판독으로 설명하지 않는다.

VLM은 대표 흐름과 분리해 짧게 보여 준다. 읽기 어려운 이미지에서 후보를 제시하는 실제 로컬 호출을 준비하고, 원문에 맞는 후보를 사람이 선택해 저장한다. 모델이 가린 숫자를 추측한 사례도 소개한다. 고정 응답을 재생했다면 화면과 멘트에 **UI 동작 재현**이라고 표시한다. HTML 시안은 앱의 실제 동작 증거로 사용하지 않는다.

### 리허설에서 확인할 것

시연 목표 버전에서 위 흐름을 실제로 한 번 이어서 실행한다. 파일·필드 수정에 따른 revision 변화, 부분 회신 기록, 재발행 후 비교, 대표 권한과 재결재를 확인한다. 마지막에 XLSX/ZIP의 실제 저장·압축 해제와 가림 범위를 확인한다. 아직 확인하지 않은 동작은 성공 화면을 만들어 채우지 않는다.

최종 앱 테스트·빌드와 캡처는 같은 버전으로 맞춘다. 현재 다른 작업의 프런트 실패·타입 오류가 보고돼 있어, 버튼 이름 변경 때문인지 실제 동작 회귀인지 해당 화면 작업에서 확인해야 한다. 최종 로그를 확보하기 전에는 “전체 테스트 통과” 또는 전체 기능 완료로 표기하지 않는다.

## 5. 기술·검증 장표에 넣을 정확한 내용

### 구조와 AI 역할

- 구조: 브라우저→API→업무 DB·원본 저장소, 서버 PC의 Ollama 로컬 모델. 핵심 구조는 [아키텍처](../architecture/overview.md)와 [ERD](../architecture/erd.md)를 따른다.
- 색인: 계약 ID, 서류 종류, 논리 문서·버전, 구조화 필드, 원문 근거를 연결한다. 의미 검색·RAG 질의응답 구현으로 설명하지 않는다.
- 텍스트 LLM: 활성화됐을 때 규칙이 해결하지 못한 대상 칸을 보완한다. 근거 가드를 통과한 값은 저장 필드에 반영되지만 사람 확인은 별도다. 실제 출처가 규칙인 값을 AI 성과로 세지 않는다.
- VLM: 버튼으로 PDF 현재 쪽·이미지를 재판독하고 후보를 제시한다. 사람이 선택한 값만 저장한다. 모델이 내놓은 근거 문장을 독립적인 원문 검증으로 간주하지 않는다.
- 검사·결재: 규칙이 등록 기준과 저장값을 검사한다. LLM이 승인이나 지급을 결정하지 않는다. 필수 서류·원본 누락은 승인을 막지만 FAIL/REVIEW는 확인 동의와 의견을 통해 승인될 수 있다.
- 근거 좌표: 실제로 확인한 좌표만 표시하고 없으면 쪽·줄을 사용한다. 텍스트 가드 평가와 bbox 하이라이트 구현을 같은 기능으로 설명하지 않는다.

세부 조건과 모델 준비는 [AI 파이프라인](../ai/pipeline.md)·[실행 설정](../ai/runtime_settings.md)·[검수 규칙](../validation/current_rules.md)을 따른다.

### 평가 장표

본문 표는 같은 test2의 네 조건으로 만든다. 규칙만 **187/204(91.67%)**, LLM만 **184/204(90.20%)**, 규칙+LLM 가드 없음 **199/204(97.55%)**, 가드 v4 적용 **195/204(95.59%)**다. 가드가 무조건 정확도를 높였다는 해석과 “95% 자동 업무 처리” 표현은 사용하지 않는다.

표 아래에는 합성 계약 6건·PDF 36개, 양쪽 모두 ABSENT인 48칸을 제외한 204필드임을 적는다. 정답은 사람 직접 라벨 확인 39칸·사람 관찰 후 기준 적용 1칸·두 AI 초안 일치 164칸이다. FAIL/MISSING 정답·누락 서류 사례가 없어 해당 검출 성능은 이 표로 평가하지 못한다. 이 한계는 본문에서 말하고 자세한 분포는 부록에 둔다.

v3 test와 v4 test2는 다른 세트이므로 정확도를 개선 화살표로 연결하지 않는다. v3 test에서 정답과 일치한 제안 100개를 가드가 보류한 사례는 원문 근거·라벨 처리의 실패 분석으로 소개한다. test2에서 가린 합계 1칸을 보류한 사례와 정답 제안도 보류한 비용을 함께 설명한다. 잘못된 PASS가 모든 조건에서 0/7이므로 일반적 안전성 우월성은 입증되지 않았다.

VLM 별도 연결 시험은 합성 이미지 4장·20항목의 19개 일치와 가린 합계 추측 오답 1개다. 작은 연결 점검이며 실무 정확도 95%로 일반화하지 않는다. 이후 추가된 예금주 규칙도 기존 test2 평가에 포함되지 않는다. 고정 예측·정답 이력·해시를 보존한 평가 방법을 설명하고 다시 모델을 실행해 발표 수치를 바꾸지 않는다.

### 안정성·운영 장표

최종 버전의 실제 테스트 명령·결과·로그는 [최신 검증 기록](../development/verification_latest.md)에서 확인한다. 과거 통과 수나 실패 보고를 현재 결과로 재사용하지 않는다. 원본 저장소 전체 검증과 제출 ZIP에 포함한 테스트의 범위를 구분하고, 발표·시연 코드와 ZIP 파일 해시가 같은 버전을 가리키는지 확인한다. 테스트 수는 정확도나 무결함 보장이 아니다.

돈·정보·업무 연결에 영향을 주는 사례를 고른다. 두 탭의 오래된 자료 저장 충돌, 역할별 결재 차례, 자료 변경 시 승인 무효화, 업로드 실패 재시도, 지급 후 변경 시 같은 지급 재확인 등이 후보다. 소스의 테스트 존재와 실제 UI 재현 결과는 따로 표시한다.

로컬 모델 경로를 보여 주되 유출 0%·운영비 0원·완전한 망분리 검증을 주장하지 않는다. 가림은 화면·원문·내보내기·요청 문구에 따라 범위가 다르다. XLSX/ZIP은 일반 전달 기능이며 모든 ERP 업로드 호환을 입증한 것은 아니다. 소스 실행·백업과 고객용 Setup 설치 완료도 구분한다.

## 6. 발표용 리서치: 좁은 질문에 답한다

조사 질문은 **“같은 가상 계약의 증빙 검토·보완·결재를 기존 도구로 처리할 때, 공식적으로 지원되는 단계와 사용자가 확인해야 할 단계는 무엇인가?”**다. 기능이 없다는 결론을 찾기보다 해당 기능이 있다는 증거부터 찾는다. 우리 앱의 구현 범위를 설명할 근거를 모으되 실무 효과·판매 가능성은 별도 검증으로 남긴다.

### 먼저 확인한 공식 자료

확인일은 2026-10-07이다. 공식 소개는 업체가 설명한 기능의 증거이며 직접 사용 성공의 증거는 아니다. “기존 업체는 단건 영수증만 처리한다”, “모두 100% 육안이다”라고 일반화하지 않는다. ERP에 자동 매칭이 존재하는지 살필 때는 [SAP Ariba 공식 송장 검증 문서](https://help.sap.com/docs/buying-invoicing/invoicing-data-import-and-administration-guide/configuring-goods-receipt-based-invoice-verification)도 참고하되, 기업 규모·입력 데이터·설치 환경을 우리 시범 가정과 동일하게 취급하지 않는다.

### 추가 조사 순서

1. 위 가까운 대체 수단 3개의 공식 사용자 매뉴얼·도움말·공개 시연·API·릴리스 문서를 찾는다. 매뉴얼과 API 문서도 1차 자료다. 홍보 문구를 실행 결과로 바꾸지 않는다.
2. 같은 사례의 단계별로 입력이 원본 PDF/이미지인지 기존 ERP 구조화 데이터인지, 대조 기준·자동 처리·사람 행동·결과 기록·예외 복구를 적는다.
3. 지원 수준을 **지원 / 일부 지원 / 명시적 미지원 / 확인 불가**로 구분한다. 기본 기능·유료 옵션·외부 연동·맞춤 개발과 제품 버전도 분리한다. 검색에서 못 찾은 기능을 미지원으로 쓰지 않는다.
4. 팀이 이미 접근할 수 있는 체험판·공개 시연이 있으면 합성 자료로 확인하고 화면을 남긴다. 한 화면에서 발견하지 못했다고 제품 전체에 없는 것으로 결론 내리지 않는다. 직접 확인이 안 되면 그대로 “직접 사용 미검증”으로 적는다.
5. 현업 경험자의 의견은 가능할 때만 받는다. 동의하에 익명·경력 맥락을 기록하고 소수 의견을 업계 전체의 실태로 일반화하지 않는다. 실제 회사 접근이나 인터뷰가 어려워도 발표 준비를 중단할 필요는 없다.

문의·계정 생성·유료 결제·외부 연락은 이 계획의 실행에 포함되지 않는다. 가격 공개가 없으면 “문의 필요”로 두고 추정 가격을 발표에 넣지 않는다. 우리 운영 비용도 PC·모델 준비·관리·지원 비용을 확인하기 전에는 0원으로 쓰지 않는다.

### 필요한 산출물은 세 가지

- **단계별 비교표 1장:** 위 3개 도구/조합과 우리 앱의 입력·대조·보완·회신·재발행·결재·전달 범위. 빈칸을 추측으로 채우지 않는다.
- **근거 카드 3~5개:** 주장, 공식 URL, 자료 종류, 확인일, 제품/옵션, 실제 확인 범위, 말할 수 없는 범위. 부록에서 원문으로 돌아갈 수 있게 한다.
- **발표용 위치 설명 1장:** “기존 제품도 문서·경비·결재 자동화를 제공한다. 이 프로젝트는 계약 증빙 원문 확인과 이후 처리 기록을 로컬 실행 시제품으로 연결해 구현·검증했다.” 독점이나 고객 구매 효과의 증거로 사용하지 않는다.

세부 조사 요청문은 [리서치 브리프 2부](app_overview_research_brief.md#2부-심층-리서치에-붙여-넣을-요청문)를 사용한다. 심층 리서치 결과의 인용 링크를 직접 열어 주장과 자료의 범위를 맞춘다. 긴 결과 문서 자체를 근거로 대신 인용하지 않는다.

| 텍스트 LLM 보완과 VLM 후보 선택을 구분했다 | [AI 파이프라인](../ai/pipeline.md), 실제 모델·활성화 설정, 저장 전후 화면 | 실제 호출/재생 및 규칙/AI 출처 표시 |
| 합성 test2에서 네 조건을 비교했다 | [평가 원본](../eval/test2/final_four_modes.md)과 고정 예측·정답 출처 | 고정 결과 있음. 분모·제한을 표와 같이 기재 |
| 최종 제출 버전에서 회귀·빌드 검증을 수행했다 | 최종 커밋/작업 트리 상태·실행 명령·날짜·결과 로그 | 최신 프런트 실패·타입 오류 정리 후 결과 확정 |
| 가까운 대체 제품도 관련 기능을 제공한다 | 위 공식 소개·매뉴얼과 추가 단계별 확인 | 관련 기능 존재 확인. 세부 범위는 확인 불가 유지 가능 |
| 고객의 확인 부담을 줄일 수 있다 | 같은 과제의 수동/앱 작업시간·오류·재확인 수·사용자 의견 | 가치 가설. 실제 절감 수치·구매 의향은 미검증 |
| 팀이 문제를 나누어 해결하고 개선했다 | 실제 팀원·산출물·해결 과정·후기 | 팀원에게 실제 기여 내용 취합 필요 |

최종 테스트 수를 제외하고 고정 평가 결과를 새 기능 검증 수치로 갱신하지 않는다. 기능 추가로 test2의 검증 범위가 소급해서 넓어지는 것은 아니다.

## 8. 팀이 지금 준비할 순서

1. **이 이야기와 가상 계약을 먼저 고정한다.** 기능 목록부터 장표를 만들지 않는다. 발표 시간만 확인해 위 시간 배분을 조정한다.
2. **실제 앱 증거를 확보한다.** 한 계약의 원문·요청·부분 회신·고친 본·결재·자료 변경을 같은 버전에서 연결해 녹화한다. AI 호출 지연에 대비해 검증한 녹화와 실제 실행을 구분해 준비한다.
3. **기술·검증 두 장을 먼저 완성한다.** 구조도와 AI 역할, 같은 test2 네 조건 표, 실패 원인·한계를 채운다. 코드와 수치로 설명할 수 있는 성과를 먼저 확보한다.
4. **시장 비교는 공식 근거가 있는 한 장으로 만든다.** 가까운 세 대상의 세부 기능이 모두 확인될 때까지 기다릴 필요는 없다. 확인 불가를 남겨도 정확한 위치 설명은 가능하다.
5. **실제 팀 역할·후기를 넣고 전체 리허설한다.** 발표 준비 담당과 개발 기여를 구분하고, 최종 UI·실행 안내·평가 수치·자료 버전을 맞춘다.

준비 업무는 4묶음으로 나눌 수 있다: 앱 사례·화면/녹화, 기술 구조·평가 근거, 공식 시장 자료·출처 검증, 장표 통합·실제 역할 취합·리허설. 담당 이름은 팀이 정한다. 아래 표의 기여는 실제 활동을 확인해 작성한다.

| 무엇이 프로젝트의 강점인가요? | 값·근거·문서 버전 연결, 판독/서류 오류 구분, 부분 회신·재발행, 자료 변경 후 재결재를 같은 업무 흐름에서 보여 준다. 각 동작을 실제 화면·코드·테스트로 뒷받침한다 |
| AI를 왜 썼나요? | 다른 서식의 텍스트에서 규칙이 해결하지 못한 필드를 보완하고 이미지 재판독 후보를 제공한다. 같은 세트의 네 조건 결과로 효과와 비용을 설명한다. 모든 조건에서 AI가 더 좋다고 말하지 않는다 |
| 95.59%면 대부분 자동 처리되는 건가요? | 합성 test2 204필드의 추출 정확도다. 업무 자동 처리율·실무 오류 감소율·누락 검출률과 다르며 정답 출처와 미평가 범위를 밝힌다 |
| 사람이 확인한다면 편리해진다는 근거는요? | 요청 문구·기한·기록을 한 번으로 묶고 원문·버전·처리 기록을 연결한 동작을 보여 준다. 실제 시간 절감은 같은 과제의 비교 측정 전이라 수치로 주장하지 않는다 |
| 예금주가 같으면 안전한 계좌인가요? | 이름 정규화 일치일 뿐 실제 은행 소유 인증이 아니다. 다른 이름·미추출은 REVIEW로 남기고 사람이 확인한다 |
| AI 오답은 어떻게 다루나요? | 텍스트 근거 가드·출처 표시·원문 확인·VLM 선택 저장·수정 이력을 구분해 설명한다. 이 절차가 모든 오답이나 잘못된 판단을 막는다고 보장하지 않는다 |
| 3~5인 결재나 ERP 연동도 가능한가요? | 현재는 최대 2단계 결재와 일반 XLSX/ZIP 전달 범위다. 자유 결재선·전용 ERP 자동 전표 연동은 후속 범위이며 구현된 것으로 발표하지 않는다 |

| 사업화는 어떻게 생각하나요? | 대상 업무와 구현 범위는 정했지만 고객 수요·작업시간 효과·운영 총비용·지불 의사는 미검증이다. 실제 사용자 과제 비교와 기존 도구 병행 평가부터 진행할 계획이라고 답한다 |

질문에 답할 때 기능의 증거는 코드·화면·회귀 검증, 추출 성능의 증거는 고정 평가, 시장 기능의 증거는 공식 자료, 업무 가치의 증거는 사용자 비교 측정으로 나눈다. 한 종류의 근거로 다른 종류의 주장을 대신하지 않는다.
